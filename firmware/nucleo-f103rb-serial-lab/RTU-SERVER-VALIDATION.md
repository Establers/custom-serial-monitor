# HEX 요청/응답 슬레이브 검증 — 2026-11-07

펌웨어 **1.5.0**을 NUCLEO-F103RB에 기록·읽기 검증하고 COM3에서 실제 HEX 요청/응답을 확인했다.
종료 시 보드는 조용한 RTU 모드이며 검사기의 COM3 연결은 닫았다. GUI 화면 조작은 하지 않았다.

- 보드: STM32F103RBT6, device ID 0x410, flash 128KiB
- ST-LINK: `066FFF485753667187145434`
- 기록 주소: `0x08000000`, BIN 15,316바이트
- BUILD 응답: `BUILD version=1.5.0 protocol=1 id=3C7C230A7FB39BA6`
- BIN SHA-256: `501AC7BFD13C6963483A4CC90BB49A095921E82FFEF2DF31FFCCF497EF9EB0B9`
- 이미지·manifest: `build-rtu-server/`
- 이전 flash 전체 백업: `backups/066FFF485753667187145434-20261107-211222-874.bin` (131,072바이트)
- 백업 SHA-256: `3CC65F48651A5AC92C8BF7FAC0C583C1FCDCB0CD708CA56D6F98F9344E607348`

기록 전에 대상 ID·flash 용량·BIN/manifest 해시와 전체 백업을 확인했다.
STM32CubeProgrammer의 다운로드 검증 성공 후 리셋했다. 옵션 바이트 변경·mass erase는 하지 않았다.

## PC 검사

- ARM GCC 12.3.1 빌드 성공: FLASH 15,316 / 131,072바이트, RAM 15,392 / 20,480바이트. RAM에는 링크 스크립트의 stack/heap 예약이 포함된다.
- 네이티브 C **472개** 통과: RTU 무음 부팅, 분할/잘림/초과/손상 입력, 타이머 순환, 큐 역압·단일 응답, 모든 다른 장치 ID의 무응답, 기존 LAB 회귀 포함.
- 별도 PC 고정 데이터 계약 검사 **81개** 통과. 기존 Modbus fixture 10종과 큐 누락 집계 회귀 통과.
- 실제 C 출력 RTU 응답 9종을 독립적인 .NET CRC/응답 계산과 앱 분석기로 대조해 통과.
- 실제 RTU HEX 요청을 담은 CLI 정의와 GUI v3 RX Check 가져오기 검사 통과.
- PowerShell 코드 파싱과 WireCodec 검사 통과.
- 변경 중인 앱 파일에 의존하지 않는지 확인하기 위해 `eaf156cd`의 별도 archive에 이번 펌웨어 변경만 적용해 빌드·검사했다. 이 archive 이미지 ID는 `71A2FF6561268A2F`이다. 파일 개행도 빌드 입력 해시에 포함되므로 실제 보드 이미지 ID와 구분한다.

## 실제 UART 검사

설정: **COM3 / 115200 / 8N1 / 흐름 제어 없음 / native idle timeout 40ms**.
앱의 `SerialService`로 한 번씩 HEX 바이트를 보내고 매번 550ms 수신했다. 관측·검사기의 자동 재전송은 없다.
원본 요청/응답을 저장한 다음 앱 분석기에 RX를 재생해 집계를 확인했다. 실기 **17종 전부 통과**했다.

| 요청 종류 | 확인 결과 |
| --- | --- |
| FC03 주소 0, 수량 2 | `01030400FA0064DBE9`, 값 250/100, CRC 정상 |
| 주소 0x0200 | `018302C0F1`, 예외 02, CRC 정상 |
| 주소 0x0100, 수량 2 | `01030400FA0064DBE8`, 의도한 CRC 오류 정확히 1개 |
| FC04 주소 1, 수량 1 | `0104020064B8DB`, 값 100 |
| 수량 0 / 126 | 각각 예외 03 |
| 미지원 FC06 | 예외 01 |
| 방송 / 다른 ID / 손상 요청 CRC | 각 550ms 창에서 수신 0바이트 |
| 잘린 요청 / 손상 프레임 안의 정상 요청 / 256바이트 초과 | 각 창에서 수신 0바이트; 내부 프레임 실행 안 함 |
| 잘림·손상·초과 후 정상 요청 | 모두 정상 응답 복구 |

처음 세 교환을 TX/RX 모두 분석하면 **결과 6, TX 3, RX 3, CRC 정상 5, CRC 오류 1, 예외 1, 불완전 0, 분석 큐 누락 0**이었다.
각 실제 RX 응답을 별도로 분석해도 기대 집계와 일치했다.
보드 `STATUS?`는 `rx_drops=0 uart_errors=0 tx_rejected=0`이었다.

실기 증거: `results/rtu-server-20261107-211416-790/`의 `report.json`, `*.tx.bin`, `*.rx.bin`.
검사기 SHA-256: `4AAEF5E1667E453EED1C120230D6513BC24E0650F7029832ADB4EA61A75F209D`.
분석기 SHA-256: `D12B6D987223618B72F1988DA82B9C15C5EBAA71DE07DECC647F44041A63CAAF`.
BIN·백업·원본 증거는 로컬 생성물이며 Git에서 제외한다.

첫 시도에서는 ST-LINK의 기록 전 리셋에서 남은 이전 BOOT/READY 바이트가 ID 응답 앞에 함께 관측되어 검사를 실패 처리했다.
검사기에 송신 전 수동 버퍼 배출 관측 창을 추가한 후 새 증거 디렉터리에서 다시 검사했다. 최종 창의 잔여 데이터는 0바이트였다.
프레임 판정을 느슨하게 하거나 잘못된 응답을 통과시키지는 않았다.

GUI 렌더링·실시간 Protocol 탭 배선·전기적 RS-485 전환·엄밀한 RTU t1.5/t3.5 적합성은 이 검사의 범위 밖이다.
사용자가 직접 따라 할 HEX 요청과 화면 기대값은 [시험 안내](MODBUS-RTU.md)에 있다.
