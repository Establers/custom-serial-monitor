# 개발 세션 및 커밋 지침

이 저장소의 기본 작업 흐름은 **요청 범위 확인 → 구현 → 검증 → 변경 검토 → 로컬 커밋 → 결과 보고**다.
완료한 변경은 해당 작업 세션에서 커밋한다. 다음 세션이나 릴리스 시점까지 모아 두지 않는다.
이 지침은 코드, 테스트, 스크립트, 설정, 문서 변경에 적용한다. AI 작업자의 필수 규칙은
루트 [AGENTS.md](../AGENTS.md)에 있으며, 사용자의 명시적인 지시가 우선한다.

## 1. 작업과 커밋의 단위

- 기본 단위는 사용자가 요청한 하나의 완료 가능한 작업이다. 관련 구현·테스트·문서를 함께 커밋한다.
- 같은 채팅에서도 독립적인 작업이 끝나면 먼저 커밋하고 다음 작업을 진행한다. 큰 작업은 검증 가능한 단계로 나눈다.
- 파일 하나를 고칠 때마다 커밋하지 않는다. 빌드되지 않는 중간 상태나 서로 다른 기능을 한 커밋에 섞지 않는다.
- 조회·상담만 했거나 실제 변경이 없으면 커밋하지 않는다. 커밋 수를 맞추기 위한 빈 커밋은 만들지 않는다.
- 사용자가 커밋 보류를 명시한 경우 그 지시를 따른다. 그 외에는 로컬 커밋을 위한 재확인을 요청하지 않는다.

## 2. 시작할 때 기존 변경 확인

저장소 루트에서 현재 작업 위치와 기존 변경을 확인한다.

```powershell
git branch --show-current
git log -1 --oneline
git status --short
git diff --stat
git diff --cached
```

기존 수정·신규 파일과 staged 변경을 이번 작업의 기준 상태로 기록한다. 기존 변경이 있어도
독립적인 작업은 진행할 수 있다. 다만 파일의 변경 주체를 추측하거나 기존 변경을 함께 커밋하지 않는다.
작업 트리를 깨끗하게 만들려고 기존 변경을 되돌리거나 stash하지 않는다.

같은 파일에 기존 변경이 있으면 diff를 먼저 읽고 이번 요청에 해당하는 부분만 수정·스테이징한다.
이전 미커밋 구현에 의존하는 작업은 필요한 선행 변경의 범위와 검증 상태도 확인한다.
커밋 경계를 안전하게 분리할 수 없다면 독립적으로 진행 가능한 작업부터 마치고,
분리할 수 없는 부분과 이유를 사용자에게 알린다.

공유 작업 폴더에서 다른 세션의 변경이 새로 나타나면 시작 시점의 기록과 다시 비교한다.
별도 브랜치가 필요하면 `codex/` 접두사를 사용하며, 다른 세션이 쓰는 작업 폴더의 브랜치를 임의로 바꾸지 않는다.

## 3. 구현과 검증

아키텍처와 안정성 규칙은 [AGENTS.md](../AGENTS.md)를 따른다. 요청과 관계없는 정리나
서식 변경은 섞지 않는다. 동작을 바꾸면 필요한 회귀 검증과 사용자 문서를 함께 갱신한다.

| 변경 범위 | 커밋 전 확인 |
| --- | --- |
| 문서만 변경 | 내용·로컬 링크·명령 경로 검토, 대상 파일의 `git diff --check` |
| C# 구현·프로젝트 설정 | 영향받는 프로젝트 빌드와 관련 테스트; 공통 경로·의존성 변경은 솔루션 검사로 확대 |
| WinUI·터미널 UI | 관련 빌드·자동 검사와 변경된 사용자 동작 확인; 실행하지 못한 GUI 검증은 명시 |
| JS·PowerShell·플러그인 | 해당 스크립트·패키지 검증; 연결되는 앱 동작도 영향에 따라 확인 |
| 시리얼 수신·로그·취소·큐 | 관련 회귀 검사, 경계·오류·취소·메모리 제한 확인; 실제 장치·장기 시험 실행 여부 구분 |

전체 솔루션을 확인할 때는 저장소 루트에서 다음 명령을 사용한다.

```powershell
dotnet build SerialMonitor.WinUI\SerialMonitor.WinUI.sln -c Release
dotnet test SerialMonitor.WinUI\SerialMonitor.WinUI.sln -c Release --no-build -m:1
```

`--no-build`는 같은 소스와 설정으로 빌드에 성공한 뒤에만 사용한다. 변경 범위에 맞는 검증이
통과하면 불필요한 반복 실행 없이 변경 검토로 넘어간다. 문서만 바꾼 작업에 앱 전체 빌드를 요구하지 않는다.

이번 변경 때문에 생긴 실패는 수정한 뒤 다시 확인한다. 기존 실패와 환경 제약은 근거와 영향을
구분해서 남기고, 필수 검증을 막으면 완료로 처리하지 않는다. 실행하지 않은 검사를 통과했다고 쓰지 않는다.
실물 UART나 장시간 안정성 검사를 자동 테스트 결과로 대신했다고 표현하지 않는다.

## 4. 검토 후 해당 작업만 커밋

이번 작업에 해당하는 실제 경로를 지정한다. 아래 `AGENTS.md`와 지침 파일은 문서 작업의 예시다.

```powershell
git diff -- AGENTS.md docs/development-workflow.md
git diff --check -- AGENTS.md docs/development-workflow.md
git add -- AGENTS.md docs/development-workflow.md
git diff --cached --check
git diff --cached --stat
git diff --cached
git commit -m "docs: define per-task session commits"
```

`git add .`, `git add -A`, `git commit -am`은 사용하지 않는다. 같은 파일의 일부만 이번 작업에
해당하면 `git add -p -- <경로>` 등으로 해당 hunk만 선택하고 staged diff를 확인한다.
새 파일은 일반 diff에 나오지 않으므로 파일 내용도 직접 읽고 staged diff에서 다시 검토한다.

위의 일반 `git commit` 예시는 index에 이번 작업만 있을 때 적용한다. 이미 다른 작업이 staged되어
있다면 그 상태를 보존하고 이번 작업만 포함하는 방법을 선택한다. 대상 파일 안에도 기존 staged
변경이 섞여 있다면 경로 지정만으로 분리됐다고 판단하지 않는다. 안전하게 분리할 수 없으면 이유를 보고한다.

커밋 내용만 체크아웃해도 필요한 구현·테스트·문서가 함께 있어야 한다. 다른 미커밋 파일이 있어야만
빌드되거나 동작하는 커밋은 완료된 작업으로 취급하지 않는다.

커밋 메시지는 `feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:` 중 목적에 맞는 접두사와
구체적인 변경 내용을 사용한다. 훅을 우회하지 않으며, 커밋 실패 시 원인을 해결하고 다시 시도한다.
로컬 커밋과 push·릴리스·배포는 별개다. 원격 반영이나 기존 커밋 수정은 사용자 요청이 있을 때만 한다.

## 5. 끝내기 전 확인과 보고

```powershell
git log -1 --oneline
git show --stat --oneline HEAD
git status --short
```

- 이번에 완료한 변경이 의도한 커밋에 모두 들어갔는지 확인한다.
- 시작할 때 있던 다른 변경과 staged 상태가 유지됐는지 확인한다. 전체 작업 트리가 깨끗해야 하는 것은 아니다.
- 마지막 답변에 변경 요약, 검증 결과, 커밋 해시를 적는다. 이번 작업의 남은 변경이나 검증 제약이 있으면 함께 알린다.
- 커밋하지 못했으면 구체적인 이유와 남은 파일·작업을 밝힌다. 완료했다고만 말하고 다음 세션으로 넘기지 않는다.

보고 예시:

```text
변경: 로그 내보내기 파일명 충돌 수정
검증: 관련 빌드와 회귀 테스트 통과
커밋: <실제 커밋 해시> fix: avoid log export filename collisions
남은 사항: 실제 장치 장기 시험 미실행; 시작 전부터 있던 다른 변경 유지
```
