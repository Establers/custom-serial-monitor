# 로그 내보내기 동시 실행 검토 — 2026-10-27

## 동작과 검증 범위

실시간 `FileLogWriter`와 보관 로그 `LogHistoryExporter`는 서로 다른 파일과
스트림을 사용한다. 내보내기는 RX/파싱/실시간 파일 대기열을 소비하거나
정지시키지 않는다. 실시간 로깅 중에도 별도 파일로 내보낼 수 있다.
현재 사용 중인 로그 경로는 ViewModel에서 거절하며, 경로 우회나 회전 중 경합이
있어도 실시간 writer의 `FileShare.Read`가 열린 파일의 교체를 막는다.
UI에서는 선택 창을 포함해 한 번에 한 건만 내보낼 수 있다.

내보내기 버튼을 누른 시점에 UI 보관 기록을 복사한 뒤 저장창을 연다.
저장창에서 이름·경로를 고르는 동안 새로 들어온 기록은 포함하지 않는다.
기본 파일명은 `첫 기록의 로컬 날짜·시각_to_버튼 클릭의 로컬 날짜·시각_logs.log`이며
양쪽 시각에 밀리초를 포함한다. 보관 한도로 제거되거나 Clear로 지운 기록은
파일명 시작 시각과 내용 모두에서 제외된다. 저장창이 열려 있는 동안에도
스냅샷이 원래 기록의 참조를 유지하므로 아래 메모리 유지 한계가 적용된다.

기존 테스트는 writer를 시작한 뒤 내보내기가 끝나고 나서 실시간 데이터를
넣었으므로, 실제 쓰기 구간의 중첩을 입증하지 못했다. 새 테스트는 내보내기를
진행 도중 멈춘 상태에서 실시간 기록 2,000건이 순서대로 flush되는지 확인한다.
추가 성능 테스트는 실제 파일 두 개를 동시에 쓰면서 완료 개수와 순서를 검사한다.

## 발견 및 수정

| 항목 | 발견 내용 | 조치 |
| --- | --- | --- |
| 종료 정리 순서 | 별도 저장을 Dispose 시작 시 최대 5초 기다리지만 창의 Dispose 제한은 3초여서 핵심 서비스 정리를 지연시킬 수 있었음 | 먼저 취소하고 수신·실시간 파일·이벤트 서비스를 정리한 뒤, 마지막에 최대 500ms 대기 |

| 동시 실행 테스트 | 실시간 파일이 열려 있다는 사실만 검증 | 내보내기 지연 중 실시간 flush, 실제 100만 건 내보내기와 실시간 기록 중첩 검증 추가 |

## 남는 병목과 한계

- **같은 저장장치의 쓰기 대역폭:** 별도 파일이어도 디스크와 OS 파일 캐시는
  공유한다. 내보내기를 실시간 파일 대기열 상황에 따라 자동 감속하는 정책은
  없다. 느린 USB/네트워크 드라이브나 저장 공간 부족에서는 실시간 파일 대기열이
  밀릴 수 있다. 실시간 writer는 100,000건 또는 64MiB 예산에 도달하면 오류를
  알리고 신규 저장 접수를 중지한다. RX가 이 디스크 대기를 직접 기다리지는
  않지만 전체 시스템 과부하에 따른 간접 영향까지 배제할 수는 없다.
- **UI 스레드의 스냅샷 복사:** `GetRetainedLinesSnapshot`은 일관된 경계를 위해
  UI 스레드에서 O(보관 건수) 참조 복사를 한다. 포맷팅과 파일 쓰기는 작업
  스레드에서 수행하지만, 복사 자체는 짧은 UI 지연을 만들 수 있다. Debug
  측정에서는 100만 건 복사가 34~43ms, 최종 Release 측정에서는 3.31ms였다.
  다른 장비나 GC 상황에서도 이 시간을 유지하거나 UI 프레임 시간을 보장하는
  것은 아니다.
- **진행률 알림:** 함께 반영된 진행률 UI는 worker가 약 100ms 간격으로 최신 값
  한 개만 교체하고 UI 타이머가 읽는다. 수신/기록마다 UI 콜백을 쌓지 않는다.
  최종 Release 성능 테스트는 이 진행률 보고를 켠 상태로 실행했다.
- **저장 중 추가 메모리 유지:** 100만 건 참조 배열은 약 7.63MiB다. 이와 별도로
  저장 완료까지 원래 LogLine의 텍스트·원본 바이트 배열을 해제할 수 없다.
  느린 내보내기 도중 보관 이력이 전부 교체되면 기존 스냅샷 기록과 새 보관
  기록이 동시에 남을 수 있다. 따라서 추가 상주 메모리를 7.63MiB로 한정해서는
  안 된다. 보관 한도와 동시 내보내기 한 건 제한 덕분에 건수는 유한하다.
- **파일 시스템 지연:** 취소 토큰은 확인하지만 동기 파일 열기/이름 변경이나
  OS에서 끝나지 않는 I/O를 강제 종료하지는 못한다. 앱의 핵심 종료 정리를
  내보내기보다 우선하며, 강제 종료나 정리 실패 시 임시 파일이 남을 수 있다.

## 줄 길이와 UX 해석

스냅샷은 문자열 내용을 읽지 않고 참조만 복사하므로 줄 길이에 따른 추가 복사를
하지 않는다. 하지만 실제 파일 저장은 UTF-8 바이트 수만큼 작업한다. 예를 들어
줄당 본문이 평균 1KB면 100만 줄은 약 1GB, 10KB면 약 10GB이며 메타데이터가
추가된다. 보관 한도는 기록 건수 기준이고 총 바이트 기준의 한도는 아니다.
긴 기록이 많으면 보관 메모리와 내보내기 중 유지하는 메모리도 커진다.

약 26만 문자 길이의 한글/이모지/개행 혼합 기록은 버퍼 경계를 넘어도 동일한
내용으로 저장하는 테스트를 통과했다. 이것은 긴 줄의 저장 정확성 검증이며,
100만 줄 모두가 긴 경우의 자원 사용량을 실측한 결과는 아니다.

따라서 화면을 막지 않는 진행률·취소 패널은 유지한다. 발견성을 위해
`로그 내보내기...`를 상단 Start Logging / Stop Logging 바로 오른쪽에 아이콘과 글자로 노출했다.
Log 탭과 우클릭 메뉴에서도 같은 작업을 실행한다.
실제 창에서의 수신·내보내기·진행률·취소 및 문구 비교는
[GUI 검증 기록](log-export-ux-validation.md)에 별도로 기록했다.

## Debug 비교 측정

같은 PC, .NET 8 Debug, OS 캐시를 사용하는 로컬 임시 파일에서 별도 측정했다.
보관 기록은 서로 다른 약 100자 ASCII 본문과 원본 바이트를 가진 100만 건이며,
저장 파일은 약 123.98MiB다. 실제 WinUI/WebView2와 UART는 실행하지 않았다.
실시간 기록 40,000건을 200건 단위로 20ms 대기하며 주입했으며, 실제 완료 시간은
약 6초로 약 6,600건/초였다. 아래는 내보내기를 켠 두 번의 측정 범위다.

| 측정값 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 내보내기 완료 시간 | 466~495ms | 337~363ms |
| 내보내기+실시간 쓰기 누적 관리 할당 | 약 401.5MiB | 약 65.8MiB |
| 실시간 쓰기 단독 누적 관리 할당 | 약 64.9MiB | 약 64.9MiB |
| 차감한 내보내기 추가 누적 할당 | 약 336.6MiB | 약 0.9MiB |
| 실시간 등록 p99 | 2.1µs | 2.2~2.3µs |
| 실시간 대기열 최대 건수 | 200 | 190~200 |
| 실시간 드롭 / 파일 오류 / 순서 오류 | 0 | 0 |

누적 할당은 상주/최대 메모리가 아니며, 스냅샷 생성 이후 구간을 측정하므로
참조 배열 7.63MiB와 유지 중인 원본 기록은 위 할당 차이에 포함하지 않는다.
측정에는 테스트 코드와 JIT·스케줄링 비용이 포함된다. 몇 번의 로컬 캐시 측정은
느린 저장장치, 디스크 부족, 긴 HEX 기록, 실장비 장시간 운전의 보장이 아니다.

## 최종 Release 측정

진행률 보고를 켠 최종 Release 실행에서 100만 건 참조 복사는 3.31ms / 7.63MiB였다.
내보내기는 301~341ms였고 약 123.98MiB 파일을 생성했다.
실시간 등록 p99는 1.6~1.9µs, 최대 대기열은 183~200건이었다. 내보내기가 끝나기
전에 실시간 기록 2,000~2,400건이 접수되고 flush되었으며, 전체 40,000건의 개수와
순서가 유지됐다. 드롭과 파일 오류는 없었다.

전체 누적 관리 할당은 실시간 쓰기 단독 약 52.7MiB, 내보내기를 병행하면
약 53.6MiB였다. 이 결과 역시 스냅샷 배열과 유지 중인 원본 메모리를 제외한
측정 구간의 누적 할당이다. 실제 UART·WebView2 프레임·외장 저장장치 측정은
포함하지 않는다.

## 현재 구현 재검증 — 2026-10-27 18:30 KST

- 100만 건 스냅샷 참조 복사는 3.61ms / 7.63MiB, 내보내기는 365.9~417.4ms였다.
  내보내기가 끝나기 전에 실시간 기록 2,600~3,000건이 접수되고 flush되었다.
  전체 실시간 기록 40,000건의 순서가 유지됐으며 드롭·파일 오류는 0이었다.
