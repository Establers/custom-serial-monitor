# Timeout 적용 경로 재검토 — 2026-09-11

사용자 기준: 200ms 설정에서 199ms 정도의 마감 차이는 허용한다. 우선 검토 대상은 설정 미적용, 이전 값 유지, 변경 신호 누락, 마감 누락이다. 제품 코드와 timeout 알고리즘은 변경하지 않았다.

## 1. 연결 완료가 최신 설정을 이전 값으로 덮을 수 있음 — 코드 경로 확인

위치: `MainViewModel.ConnectCoreAsync` 및 `StartTransportForAutoReconnectAsync`.

두 함수 모두 시작 시 `SelectedRxDisplayMode`와 `HexGroupTimeoutMs`를 로컬 변수에 저장한다. 이후 파일 준비 또는 COM 연결을 await하고, 완료 시 저장해 둔 값을 `ApplyRxDisplayRuntime`에 전달한다. 이 호출은 파이프라인 설정, 적용값 필드 및 브리지 그룹 설정을 덮는다. 반면 사용자가 선택한 `_currentUiSettings` 값은 그대로 남는다.

가능한 순서:

1. 40ms 설정으로 연결 또는 자동 재연결 시작.
2. 연결 대기 중 사용자가 500ms를 Set: 저장값과 파이프라인 모두 500ms.
3. 연결 완료: 시작 시 캡처한 40ms를 다시 적용.
4. 저장값 500ms, 실제 적용값 40ms로 불일치.

설정 화면의 timeout 입력/Set은 `IsHexRxViewSelected`에만 활성 여부가 연결되어 있으며 연결 작업의 `IsBusy`로 비활성화하지 않는다. 수신 모드에도 같은 캡처 문제가 적용된다. 실제 COM 연결을 제어한 종단 간 재현은 수행하지 않았다. 위 순서는 현재 await 및 설정 대입 경로에서 도출한 것이다.

권장 수정: 즉시 적용 설정인 수신 모드/timeout은 연결 완료 시점의 최신 값으로 적용하거나 설정 버전을 비교해 오래된 스냅샷이 최신 값을 덮지 못하게 한다. native 옵션은 현재 실제 앱 경로에서 비활성화되어 있어, 이 수정 때문에 native timeout을 새로 켤 필요는 없다.

## 2. 같은 값을 다시 Set해도 불일치를 복구하지 않음 — 실행으로 확인

위치: `MainViewModel.HexGroupTimeoutMs` setter의 같은 저장값 검사, `ApplyHexGroupTimeoutDraft`, `HasPendingHexGroupTimeout`.

setter는 저장된 값과 입력값이 같으면 파이프라인의 현재 값을 확인하지 않고 반환한다. Apply 함수는 이후 성공을 반환하며 pending 여부도 저장값과 draft만 비교한다.

실제 public Apply 메서드를 격리 호출한 결과:

```text
Set returned=True; saved=500; active=40; pending=False; hint=Active: 40 ms
```

이 확인은 WinUI 생성자를 건너뛴 MainViewModel에 저장값 500ms, 실제 LogPipeline 40ms, draft 500ms를 설정하고 실행했다. 불일치 상태의 Set 처리만 검증한 것이며 연결 자체를 재현한 것은 아니다. 일회성 진단 테스트는 제거했다. 잘못된 현재 동작을 영구적인 정답으로 고정하는 테스트는 남기지 않았다.

권장 수정: Set은 같은 저장값이어도 현재 적용값이 다르면 파이프라인/브리지에 재적용한다. 성공 및 pending 표시도 저장값과 실제 적용값의 차이를 반영한다. 이는 패킷 timeout 알고리즘 변경 없이 설정 전달 경로에서 수정할 수 있다.

## 3. 브리지의 변경 적용 시점은 화면과 다름 — 조건부 동작

`SerialBridgeService.ConfigureDeviceToVirtualGrouping`는 설정 필드만 바꾸며 현재 writer의 대기를 깨우지 않는다. 이미 큐에 들어간 바이트는 enqueue 당시 timeout을 보관한다. 현재 그룹은 기존 설정으로 처리되고 새 값은 후속 입력에 반영된다. 별도의 최대 100ms 전송 대기 제한이 있어 이것을 화면 timeout의 무기한 미적용과 동일시하면 안 된다.

브리지를 사용하는 경우 화면에서 Set한 순간과 외부 프로그램이 보는 전송 시점이 다를 수 있다. 기존 바이트의 시간 관계를 보존하려는 큐 스냅샷 정책일 수 있으므로, UI 성능 개선에 섞어서 변경하지 않는다.

## 검증한 정상 경로

`LogPipelineLiveTimeoutTests`에 총 9개 케이스를 유지한다.

- 입력 채널을 열어둔 상태에서 20/100/200ms 자연 마감: 각 20회, 조기 허용 오차 2ms.
- 대기 중 5000→1000ms 단축: 이미 지난 수신 시간을 반영하고 기존 긴 대기를 중단.
- 대기 중 1000→2500ms 연장: 이전 마감 시간에는 출력하지 않고 바이트 유지.
- 12개 패킷에 대해 각각 100회 값 변경 후 최종 40ms 적용: 총 1,200회 중간 변경 후 최종값 유효.
- 수신이 비어 있을 때 변경한 값이 다음 패킷에 적용.
- timeout 전에 새 바이트가 오면 마지막 수신부터 다시 대기하고 같은 패킷으로 유지.
- 미완료 HEX 그룹이 있는 모드 전환 후, HEX로 복귀하면 새 timeout으로 처리.

위 케이스들은 정상 파이프라인에 직접 설정을 전달하는 조건이다. 연결 orchestration의 오래된 스냅샷 덮어쓰기를 검증하거나 배제하지 않는다.

WinUI 관련 테스트 85개 통과(파이프라인, 수신 옵션/세션, native 경계, 브리지 그룹, UI 설정, 프로필 기본값 포함). 기존 Core 35개도 앞선 검토에서 통과했다. 실제 장치 및 USB 드라이버의 전달 지연은 이번 검증에 포함하지 않았다.

## 후속 수정 우선순위

1. 연결/자동 재연결 완료 후 최신 수신 모드와 timeout을 보존.
2. 같은 값을 Set해도 저장/실제 적용 불일치를 복구.
3. 비동기 연결을 의도적으로 지연시키는 통합 회귀 테스트로 위 두 경로 검증.
4. UI 문자열 가공 성능 개선은 위 설정 적용 및 timeout 경계 코드와 별개로 진행.
