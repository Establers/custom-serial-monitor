# 로그 저장 안정성 점검 (2026-09-12)

## 수정 사항

| 상황 | 기존 위험 | 개선 |
| --- | --- | --- |
| 저장 실패 / 연결 대기 | 설정만 켜져 있어도 LOG ON | 실제 writer 상태와 파일 유무로 ON / WAITING / STARTING / STOPPING / FAULT 표시. UI 타이머에서 상태 변경 반영 |
| 일시적 쓰기·flush 실패 | 복구 과정에도 정상 저장처럼 표시 | 기존의 제한된 배치 재기록 유지. 오류 이력이 있으면 WARN 및 재기록·미저장 수 표시 |
| 디스크 가득 참 | 다른 I/O 오류처럼 복구 파일 생성 재시도 | Windows 디스크 부족 오류를 구분하여 파일 저장만 중단. 공간 확보 후 OFF → ON으로 재시작 |
| 저장 대기열 포화 | 일부 로그를 버리고 계속 ON | 용량 초과를 FAULT로 표시하고 신규 접수 종료. 이미 접수된 로그는 가능한 만큼 기록. 수신/UI를 디스크 대기 때문에 막지 않음 |
| 큰 HEX/원본 데이터 | UTF-8 출력 크기만으로 메모리 제한 | 보관 중인 UTF-16 텍스트·원본 바이트 크기도 대기열 예산에 반영. 배치도 1 MiB 기준으로 flush |
| 느린 연속 입력 / 시계 변경 | 대기열 소비 중 flush 타이머 지연, 시스템 시간 변화 영향 | 매 기록 후 시간 기준 검사, 경과 시간은 Stopwatch 사용 |
| Async 메서드 자체가 반환하지 않음 | 타임아웃 감시 전에 worker가 막힘 | I/O 호출 자체를 작업 스레드로 분리하고 기존 시간 제한·지연 작업 격리 적용 |
| 시작 명령 토큰의 후속 취소 | 이미 실행 중인 저장까지 취소 | 시작 명령과 writer 생명주기 분리. 시작 도중 취소 시 정리 |
| 종료 시간 초과 | 미저장 데이터가 있어도 STOPPED | 접수된 데이터가 남아 있으면 FAULT와 미저장 수 기록 |
| 정상 연결 종료 / 재연결 | 파서와 소비자를 먼저 취소하여 마지막 데이터 누락 가능 | 시리얼 생산자 종료 → 파서 drain 및 마지막 부분 행 출력 → 소비자 완료 → 파일 flush 순서. 파서 drain은 10초 제한 |
| 화면 정지 시 저장도 중지하는 설정 | LOG ON 표시 중 의도적인 미저장 | LOG PAUSED 표시. 기본값인 화면 정지 중 저장 계속하기는 유지 |

## 검증

- WinUI 테스트 전체 413개 통과, Core 테스트 전체 35개 통과.
- 실제 임시 파일에 연속 20,000개 로그를 분할 저장한 뒤 전체 내용·순서·개수 비교.
- 수신 큐의 5,000개 패킷과 개행 없는 마지막 데이터를 파서 → 파일까지 전달한 뒤 확인.
- 주입한 디스크 부족, 지속 쓰기 실패, 쓰기·flush·open 지연, 동기적으로 막히는 Async 호출, 대기열 포화, 시작 토큰 취소, 저장 재시작 확인.
- 기존 파일 이름 충돌 방지, 날짜 변경, 크기 분할, 배치 복구, 종료 시 flush 테스트 유지.

## 보장 범위와 남는 한계

- 저장 카운터의 Durable은 StreamWriter/FileStream flush 완료를 뜻한다. 전원 차단에도 물리 매체에 영구 보존되었다는 보장은 아니다. 정상적으로도 마지막 배치는 최대 약 2초 동안 버퍼에 있고, 저장 장치가 느리면 더 길어질 수 있다.
- 복구 배치는 새 파일에 재기록한다. 실패 직전에 일부가 원래 파일에 기록되었을 수 있으므로 파일들을 합칠 때 중복 가능성이 있다. Uncertain은 이 불확실한 재기록 건수이며, Abandoned는 저장 완료를 확인하지 못하고 포기한 접수 건수다.
- 수신 속도가 처리·저장 속도를 지속적으로 초과하면 유한 메모리만으로 무손실을 보장할 수 없다. 이 경우 파일 대기열 포화를 숨기지 않고 저장 실패로 표시한다. OS/UART/수신 큐 단계의 유실은 별도 RX 오류·드롭 지표를 확인해야 한다.
- 파일은 기존과 동일한 표시용 텍스트 로그다. 바이너리 원본을 그대로 보존하는 raw 캡처 형식으로 변경한 것은 아니다.
- 실제 디스크를 가득 채우거나 USB 저장 장치를 제거하는 실험, 수일간 실제 하드웨어 연속 운전, WinUI 화면 수동 검증은 이번 자동 검증에 포함하지 않았다.

## 성능 추가 점검 (2026-09-13)

이전 기능 테스트만으로 UI 렉이 없다고 판단할 수는 없다. 이번에는 직전 개선본과 추가 최적화본의 저장 경로를 같은 PC, .NET 8 Debug 환경에서 비교했다. 정상 상태에서 40,000개 로그를 실제 임시 파일에 저장하고, 마지막 flush와 종료까지 측정했다. 첫 실행을 제외한 3회 중앙값이다. 파일은 OS 캐시를 사용하므로 느린 USB나 네트워크 저장 장치의 속도를 대표하지 않는다.

| 측정값 | 직전 개선본 | 추가 최적화본 |
| --- | ---: | ---: |
| 저장 완료 시간 | 142.0 ms | 56.3 ms |
| 프로세스 CPU 사용 시간 | 406.2 ms | 93.8 ms |
| 누적 관리 메모리 할당량 | 100.84 MiB | 65.78 MiB |
| 완료된 스레드 풀 작업 수 | 41,812 | 1,203 |
| 로그 대기열 등록 p99 | 1.40 µs | 1.10 µs |

메모리 수치는 상주 메모리가 아니라 측정 구간 전체의 누적 할당량이다. 프로세스 단위 카운터에는 테스트 코드 비용도 포함되며, 최대 지연은 GC·스케줄링에 따라 달라진다. UI 프레임 지연 측정은 아니다.

추가 변경:

- 매 줄마다 Task.Run과 타임아웃 감시를 만들던 경로를 배치당 한 번으로 변경했다. 최대 100줄 / 1 MiB / 약 2초의 flush 조건과 I/O 타임아웃을 유지했다.
- 타임아웃 후에도 실행 중일 수 있는 작업에는 변경되지 않는 배치 배열과 writer 참조를 전달하여, 후속 정리·복구와 데이터를 공유하지 않게 했다.
- 파일 관련 런타임 상태가 실제로 바뀔 때만 해당 UI 속성을 갱신한다. 일반 RX 상태 갱신마다 파일 버튼·명령 전체를 갱신하지 않는다.
- 저장 실패 후 들어오는 로그는 매번 알림을 보내지 않고 초당 최대 한 번 집계한다. 드롭 카운터는 모든 건을 기록한다.
- 전체 테스트 중 HEX idle 타이머의 간헐적인 조기 완료가 재현되어, 타이머가 깨어난 뒤 Stopwatch 기준 마감 시간을 재확인하고 짧은 남은 대기도 올림 처리했다.

검증 결과:

- WinUI 전체 416개 통과. 성능 측정은 `SERIAL_LOG_PERF=1` 환경 변수와 `FullyQualifiedName~FileLogWriterPerformanceTests` 필터로 별도 실행했다.
- 저장 장치를 막은 상태에서 추가 5,000건 등록 완료, 장치 해제 후 총 5,100건 flush 확인.
- 저장 실패 후 50,000건 거절 시 정확한 카운터와 알림 집계 확인.
- 배치 처리 변경 후 기존 순서·분할·재기록·종료·타임아웃 테스트 통과.
- 재현용 측정 로그: `artifacts/log-perf-before.txt`, `artifacts/log-perf-after.txt`.

실제 WinUI 화면과 실물 시리얼 장치를 결합한 장시간 프레임 지연은 별도 측정이 필요하다. 이번 결과는 저장 경로의 추가 부담을 줄였다는 근거이며, 모든 환경에서 렉이 전혀 없다는 보장은 아니다.
