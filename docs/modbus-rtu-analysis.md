# Modbus RTU 분석과 패킷 만들기

기존 Inspector 패널의 **Protocol** 탭에서 `Modbus RTU`를 선택한다.
그 이후 들어오는 실제 RX 원본 바이트와 기존 TX 로그의 원본 바이트를 자동 분석한다.
기본값은 `사용 안 함`이며 선택값은 프로필이나 재시작 때 자동 복원하지 않는다.
분석은 장치에 요청을 보내거나 폴링하지 않는다. `패킷 만들기`에서 요청을 작성하고
HEX를 복사할 수 있다.

## 요청 패킷 만들기

1. Protocol에서 `Modbus RTU`를 선택하고 `패킷 만들기`를 누른다. 연결 전에도 사용할 수 있다.
2. 기능을 고르고 표시되는 필드를 입력한다. 표준 요청 19종과 Custom PDU를 지원한다.
   기능 코드는 **HEX**로 표시한다. 예를 들어 `17`은 10진수 기능 23이다.
3. 숫자는 10진수 또는 `0x` 접두사 HEX를 사용한다. 시작 주소는 **0부터** 세는
   실제 프로토콜 주소다. 예를 들어 Holding Register 40001은 주소 `0`으로 입력한다.
4. 여러 쓰기 값은 주소 순서대로 공백·쉼표·세미콜론·줄바꿈으로 구분한다.
   코일은 항목마다 `0` 또는 `1`, 레지스터는 `0–65535`를 입력한다.
   수량·바이트 수·코일 비트 배치·CRC(하위 바이트 먼저)는 자동 계산한다.
5. CRC가 포함된 HEX 미리보기를 확인하고 파란 기본 버튼 `HEX 복사`를 누른다.
   복사 후에도 팝업과 작성 내용은 유지되며 `닫기`로 종료한다. 버튼과 팝업은 WinUI 기본
   스타일을 사용하고 앱의 밝게/어둡게 테마를 따른다. TX 입력이나 Terminal/HEX 모드는 바꾸지 않는다.
   전송하려면 직접 HEX 모드를 선택한 후 TX 입력란에 붙여넣고 기존 **전송 버튼**을 누른다.

입력은 기능별로 압축해 배치한다. ID와 기능은 같은 줄, 일반 읽기는 시작 주소·수량,
단일 쓰기는 주소·값(또는 ON/OFF), 여러 쓰기는 주소·자동 계산 수량을 각각 같은 줄에 표시한다.
복합 17은 읽기 줄과 쓰기 줄을 분리하고 쓰기 값 목록을 아래에 둔다. Mask Write는
주소·AND·OR 세 칸, 장치 식별은 조회 방식·객체 ID 두 칸으로 표시한다.
진단은 단일 데이터일 때 하위 기능 옆에 값 한 칸을 두고, Return Query Data는 전체 폭의
여러 값 입력란을 사용한다. Custom은 기능 코드·원시 데이터, 파일 레코드는 여러 줄 목록이다.

편집 영역은 오른쪽 스크롤바 공간을 따로 확보한다. 여러 줄 입력란도 내부 스크롤바 여백을 두며,
HEX 미리보기·오류·CRC 요약은 편집 스크롤 바깥에 표시한다. 숫자 필드는 짧은 값에 맞는 폭을
사용하지만 긴 붙여넣기를 잘라내지 않는다. 65535 등 허용 범위를 넘으면 오류와 함께 복사를 막는다.
장치 ID·주소·수량 등 단일 값과 RTU 패킷 표시의 텍스트는 세로 가운데에 정렬한다.
파일 레코드·쓰기 값 등 여러 줄 목록은 위쪽에서부터 표시한다.

HEX 복사 중 Windows 클립보드가 잠시 사용 중이면 실패한 단계만 각 최대 5회 시도한다.
단계별 재시도 간격은 50/100/150/200ms이며 대기 중 UI를 막지 않는다. 내용 설정이 성공한 뒤
앱 종료 후에도 유지하는 단계(Flush)만 실패하면 내용을 다시 설정하지 않고 Flush만 재시도한다.
같은 패킷을 복사 중인 중복 클릭은 무시한다. 미리보기 값이 바뀌면 이전 복사를 취소하고,
새 값으로 복사 버튼을 누르면 이전 작업 종료를 기다리지 않고 새 요청을 처리한다.
팝업을 닫으면 재시도를 취소하며, 취소된 작업의 완료나 오류를 새 요청의 결과로 표시하지 않는다.
계속 사용 중이거나 다른 오류가 발생하면
오류 안내와 진단 기록을 남긴다.

ID 0 브로드캐스트는 순수 쓰기 05/06/0F/10/15/16에서만 지원하며 응답이 없다.
나머지 기능과 Custom PDU는 ID 1–247을 사용한다. 일반 읽기 수량은 코일/입력 1–2000,
레지스터 1–125, 여러 쓰기는 코일 1–1968, 레지스터 1–123이다.
마지막 주소가 65535를 넘거나 값·수량이 잘못되면 미리보기를 지우고
복사를 비활성화한다. 붙여넣은 숫자와 값은 길이 제한으로 잘라내지 않고 전체 입력을 검증한다.
예를 들어 범위 밖 주소 `0x10000`을 다른 유효 주소 `0x1000`으로 바꾸거나,
패딩된 ID `0x000001`을 브로드캐스트 ID `0x0000`으로 바꾸지 않는다.
예외 응답과 TCP/ASCII 프레임 생성은 지원하지 않는다. 실제 장치의 기능 지원 여부는
제조사 설명서와 응답으로 확인해야 한다. 작성 기능과 수신 분석의 해석 범위는 별개이며,
일부 파일·진단·Custom 프레임은 분석 목록에서 CRC와 원시 HEX 중심으로 표시될 수 있다.

### 지원 요청

| HEX | 기능 | 입력 |
| --- | --- | --- |
| 01 / 02 | 여러 코일 / 이산 입력 읽기 | 시작 주소, 수량 |
| 03 / 04 | 여러 Holding / Input Register 읽기 | 시작 주소, 수량; 2 이상이면 여러 레지스터 |
| 05 / 06 | 단일 코일 / 레지스터 쓰기 | 주소, ON/OFF 또는 값 |
| 07 | Exception Status 읽기 | ID만 필요 |
| 08 | Diagnostics | 표준 하위 기능 15종, 16비트 데이터 |
| 0B / 0C | 통신 이벤트 카운터 / 로그 읽기 | ID만 필요 |
| 0F / 10 | 여러 코일 / 레지스터 쓰기 | 시작 주소, 값 목록 |
| 11 | Server ID 읽기 | ID만 필요 |
| 14 / 15 | 파일 레코드 여러 묶음 읽기 / 쓰기 | 한 줄에 파일·레코드 묶음 하나 |
| 16 | Mask Write Register | 주소, AND/OR 마스크 |
| 17 | Read/Write Multiple Registers | 읽기 주소·수량, 쓰기 주소·값 목록 |
| 18 | FIFO Queue 읽기 | FIFO 포인터 주소 |
| 2B/0E | 장치 식별 정보 읽기 | Basic/Regular/Extended/Individual, 객체 ID |
| Custom | 제조사 전용 PDU 등 | 기능 1–127, 원시 HEX 데이터 0–252바이트 |

`17`은 쓰기를 먼저 수행한 뒤 읽는 복합 요청이다. 읽기는 1–125개, 쓰기는 1–121개이며
두 주소 범위를 별도로 검증한다. 일반 `03`과 `04`의 여러 레지스터 읽기와는 별도 기능이다.

파일 읽기는 각 줄을 `파일, 레코드, 수량`으로 입력한다. 예를 들어 아래 두 묶음은
서로 다른 파일·주소를 한 요청으로 읽는다.

```text
4, 1, 2
3, 9, 2
```

파일 쓰기는 `파일, 레코드: 값 목록` 형식이다. 예: `4, 7: 0x06AF 0x04BE 0x100D`.
파일은 1–65535, 레코드는 0–9999이며 참조 유형 06, 길이와 바이트 수는 자동 계산한다.
여러 묶음의 총 요청 크기와 파일 읽기의 예상 응답 크기가 253바이트 PDU 한도를 넘으면 거부한다.

진단 하위 기능은 0000–0004, 000A–0012, 0014를 제공한다. Return Query Data는
1–125개 16비트 값, Restart는 0000/FF00, ASCII 구분자는 CHAR/00, 나머지는 0000 한 개다.
재시작·카운터 초기화·Listen Only 요청은 전송 시 장치 상태를 바꾸므로 기능별 안내를 표시한다.

Custom은 ID·기능·CRC를 제외한 **데이터 바이트만** HEX로 입력한다.
예를 들어 ID 1, 기능 `0x41`, 데이터 `00 FF 80`을 지정하면 `01 41 00 FF 80` 뒤에
CRC를 붙인다. 프레임 길이·기능 코드·CRC는 검사하지만 제조사별 데이터 의미는 검증하지 않는다.
CANopen MEI 0D 등 별도 규격이 필요한 요청도 이 경로로 작성할 수 있다.

최초 추가 시 Release 솔루션 빌드(경고 0·오류 0), Core 테스트 607개와 WinUI 테스트
1,703개를 통과했다. 장치 환경이 필요한 17개는 건너뛰었다. 별도 Debug 검증 앱에서 팝업,
범위 초과 입력과 복구, HEX 복사, 여러 레지스터 자동 수량·바이트 수를 확인했다.
실제 장치로 작성한 요청을 전송하는 검사는 하지 않았다.

복사 전용 UI 개편은 실행 중인 앱과 분리한 작업 폴더에서 Release 솔루션 빌드
(경고 0·오류 0)와 관련 테스트 109개를 통과했다. 장치 환경이 필요한 1개는 건너뛰었다.
기본 버튼 스타일과 실제 XAML의 입력 길이 제한 유무, 패딩된 ID와 범위 밖 숫자를 검증했다.
이번 개편의 수동 GUI 검사는 실행하지 않았다.

표준 요청 19종·Custom 확장도 별도 작업 폴더에서 Release 솔루션 빌드(경고 0·오류 0)와
관련 테스트 134개를 통과했다. 장치 환경이 필요한 1개는 건너뛰었다. 20개 선택지의 기본 요청,
새 입력란의 XAML 바인딩·붙여넣기 제한, 읽기/쓰기 독립 범위, 파일 요청·예상 응답 크기,
진단 하위 기능의 데이터 제약, Custom 최대 ADU 크기와 CRC를 검사했다.
확장 UI의 수동 GUI 검사와 실제 장치 전송은 실행하지 않았다.

## 화면과 보관

- 상단 툴바에서 프로토콜과 분석 상태를 확인하고 목록 비우기·통계 초기화를 실행한다.
  RX/TX와 CRC 통계는 바로 아래에 묶어서 표시한다. 보관 안내와 집계 시각은 같은 줄 오른쪽에
  표시하며 별도 하단 줄은 사용하지 않는다. 폭이 좁으면 한 줄 말줄임과 툴팁으로 전체 내용을 확인한다.
- 패킷 목록은 시간·RX/TX·ID·FC·상태·기능 열로 정렬하고, 선택한 항목의 상세는 별도 패널에 표시한다.
  빈 목록에는 시작/수신 대기 안내를 표시한다. 폭이 좁고 높이가 충분할 때 상세를 목록 아래에 배치한다.
  높이가 낮으면 두 영역을 좌우로 유지하여 상세 본문이 사라지지 않게 한다.
  작은 Inspector 높이에서도 목록과 상세는 각각 스크롤하며 고정 최소 높이로 화면을 밀어내지 않는다.
- 다른 탭으로 이동하거나 화면 로그를 일시 정지해도 백그라운드 분석은 계속한다.
- 창별로 최근 **10,000개 패킷/분석 조각**을 메모리에 보관한다. 요청과 응답은 각각 한 항목이다.
  따라서 실제 보관 시간은 패킷 수신률에 따라 달라진다.
- 결과 보관에는 별도로 **16 MiB** 예상 메모리 상한도 적용한다. 먼저 닿는 제한에 따라
  오래된 항목을 교체하고 `만료` 수를 표시한다.
  이는 결과 자료구조의 보수적인 추정치이며 프로세스 전체 RAM 한도는 아니다.
- 탭이 보일 때 최대 200 ms 간격으로 UI를 갱신한다. 숨기면 UI 목록 캐시만 비우며
  분석기의 최근 이력과 선택한 ID는 유지한다. 선택한 항목이 아직 보관 중이면 복원한다.
- 패킷 선택 시 원본 HEX, CRC 수신값/계산값, 필드와 레지스터 값을 자세히 보여준다.
  상세 문자열과 레지스터 값 확장은 선택할 때만 수행한다.
- `사용 안 함`은 새 분석을 중지하지만 이미 보관된 결과는 남긴다.
  `분석 목록 비우기`는 이력과 진행 중 조각만 무효화하며 누적 통계는 보존한다.
- 별도의 분석 파일·디렉터리·자동 내보내기는 만들지 않는다. 앱 종료 시 분석 이력은 사라진다.
  기존 시리얼 로그 저장은 기존 설정을 따른다.

## 따라가기·표시 정지·필터

- `따라가기`는 기본 ON이며 새로 표시되는 결과로 스크롤한다. 패킷 선택, 목록 위로 스크롤,
  스크롤바/터치 조작 및 목록의 방향·페이지 키 입력은 따라가기를 해제하여 읽던 위치를 지킨다.
  다시 켜면 최근 결과를 따라간다.
- `표시 정지`는 현재 목록만 고정한다. 수신·분석·누적 통계와 최근 10,000개 보관은 계속한다.
  버튼의 `재개 (+N)`은 고정된 화면 이후 발생한 분석 결과 수이며 통계 초기화와 별개다.
  탭을 왕복해도 고정 목록을 유지한다. 재개하면 현재 보관 범위로 갱신하고, 이미 만료된 선택은 안내한다.
- 정지 중에는 고정 목록에만 필터를 적용한다. 필터를 바꿔도 새 라이브 결과를 섞지 않는다.
  분석기는 정지 중 메타데이터 스냅샷만 제공하며 매 갱신마다 라이브 프레임 배열을 복사하지 않는다.
  메모리에는 라이브 보관 상한 외에 정지 시점의 bounded 스냅샷 한 개가 일시적으로 남을 수 있다.
- `필터` 팝업에서 장치 ID(10진수), FC(HEX), RX/TX, 상태를 조합하고 `적용`한다.
  빈 ID/FC는 전체이며 `03`과 `0x03`을 모두 허용한다. `03`은 예외 기능 `83`도 포함하고,
  `83`은 해당 기능만 표시한다. 잘못된 입력은 적용하지 않고 기존 필터를 유지한다.
  팝업을 적용 없이 닫으면 편집 내용은 취소된다. `필터 초기화`는 보관 결과를 지우지 않는다.
- 활성 조건 수는 필터 버튼에 표시하고, `표시 / 보관` 건수를 구분한다. 누적 통계는 항상 전체 기준이다.
  조건에 맞는 패킷이 없을 때는 필터 안내를 표시하며, 필터에서 제외된 선택과 보관 만료를 구분한다.
- 상태 열은 `CRC OK`, `CRC 오류`, `불완전`, `미해석`, `예외 XX`를 구분한다.
  CRC 오류와 예외 응답은 강조한다. CRC가 잘못된 완성 길이 후보를 상세에서 데이터 부족으로
  안내하거나 레지스터 값으로 해석하지 않는다. CRC 정상인 예외 응답도 일반 패킷과 구분한다.

형식 이름 잘림 수정은 Release 솔루션 빌드(경고·오류 0)와 관련 검사 29개를 통과했다.
GUI 실행·조작 검증은 사용하지 않았다.

해석 결과가 비어 있으면 결과 영역도 접어 교환 옵션과 미해석·오류 안내 사이에 빈 줄을 남기지 않는다.

CRC와 실제 길이가 정상이고 역할이 읽기 응답으로 식별된 FC03·04·17(HEX)의 레지스터 데이터만
해석한다. 요청을 관측하지 못한 감시 환경에서도 사용할 수 있으며, 요청·예외·CRC 오류·
불완전·역할이 모호한 패킷은 해석하지 않고 안내한다. 원본 HEX와 기존 패킷 상세는 아래에 유지한다.

각각 다른 이유를 표시한다. CRC 정상 패킷에 다시 CRC 정상 패킷을 선택하라는 안내를 하지 않는다.

안내 개선 검증: 실행 중인 앱의 DLL 잠금으로 기본 출력 폴더 빌드는 실패하여,
이번 변경만 적용한 별도 작업 폴더에서 Release 솔루션 빌드(경고·오류 0)를 확인했다.
관련 WinUI 검사 85개 통과, 장치 조건부 1개 제외. 실제 프레이머를 거친 TX 요청·감시 RX 요청의
CRC 정상 안내와 읽기 응답 선택 시 값 해석으로 전환되는 흐름을 포함한다.
Core 관련 검사는 최초 실행에서 기존 `NativeIdleBoundary_IsUsedOnlyWhenQualified` 2건이 실패했으나,
컬렉션 병렬 실행을 끈 재실행(`xUnit.ParallelizeTestCollections=false`)에서는 82개 통과했다.
이번 변경은 수신·프레이밍 로직을 바꾸지 않으며, GUI 조작 검증은 실행하지 않았다.

- 형식: UInt16 / Int16 / UInt32 / Int32 / Float32. 기본값은 UInt16, 원래 바이트·워드 순서다.
- 바이트 교환: 레지스터마다 `AB CD → BA DC`. 워드 교환: 32비트 값마다 `AB CD → CD AB`.
  두 옵션을 함께 선택할 수 있다. 16비트 형식에서는 워드 교환을 적용하지 않는다.
- 시작 위치는 응답 첫 레지스터를 `+0`으로 센다. 상태 워드 다음의 Float32를 읽으려면 `1`로 지정한다.
  실제 장치 주소를 추정하거나 요청·응답을 자동 연결하지 않는다.
- 표시값은 **해석값 × 배율**이다. 예: `00 FA`, UInt16, 배율 `0.1` → `25`.
  `41 C8 00 00`은 Float32로 `25`다. 데이터 형식·순서·배율은 사용자가 지정한다.
- 시작 위치 이후의 데이터를 선택한 형식 단위로 해석한다. 32비트 값에 필요한 두 레지스터가
  끝에서 부족하면 마지막 위치를 미해석으로 안내한다. 범위 밖 시작 위치나 유한하지 않은 배율은
  이전 해석값을 지우고 오류를 표시한다.
  입력은 잘라내지 않는다. 장치가 보낸 Float32 NaN/Infinity는 그대로 표시하고 배율 계산 범위 초과는 별도로 표시한다.
- 형식과 배율 등 설정은 창 안에서 다음 선택과 탭 왕복에도 유지한다. 프로필이나 재시작에는 저장하지 않는다.
  선택 만료·필터 제외·목록 비우기·탭 숨김·프로토콜 전환 시 해당 패킷의 해석 결과는 해제한다.

계산과 출력은 선택한 한 패킷/설정이 바뀔 때만 수행한다. 수신·분석 큐와 저장된 원본을 변경하지 않으며,
최대 125개 레지스터만 확장한다. 배율이 1인 Float32는 원래 `float` 값에 `G9` 형식을 적용하고,
배율을 적용한 결과는 `double` 값에 `G17` 형식을 적용한다. 원래 값도 같은 정밀도로 표시한다.
이는 [Microsoft의 숫자 표시 지침](https://learn.microsoft.com/en-us/dotnet/standard/base-types/standard-numeric-format-strings#general-format-specifier-g)에
따라 표시 문자열을 다시 수로 읽었을 때 원래 값을 보존하기 위한 것이다. 예를 들어 `4B 7F FF FF`는
`16777215`, 배율 `0.1` 적용 시 `1677721.5`로 표시한다. `3F 80 00 00`과 `3F 80 00 01`도
서로 다른 값으로 표시한다. NaN/Infinity 표시와 배율 범위 초과 안내는 유지한다.

정밀도 개선 검증: 이번 변경만 적용한 별도 작업 폴더에서 Release 솔루션 빌드(경고·오류 0),
관련 WinUI 검사 101개 통과·장치 조건부 1개 제외. Float32 경계값·인접값·서브노멀·최대값·
음수 0의 원본 비트 복원, 배율 적용 결과의 double 비트 복원과 한·영·독 숫자 형식을 검사했다.

## 데이터 경로와 부하 제한

`CaptureBytesReceived`의 기존 불변 RX 배열을 별도 bounded channel에 제공한다.
TX는 기존 `FanOutLogLine`에서 `RawBytes`를 제공한다. HEX 화면 문자열을 재파싱하거나
동일 COM 포트를 다시 열거나 기존 파서의 수신 채널을 경쟁해서 읽지 않는다.
Terminal/HEX 표시 모드와 파일 로깅, 표시 Pause 여부는 RX 분석의 입력을 바꾸지 않는다.
브리지에서 실제 RX는 raw capture observer를 통해 한 번만 제공된다.

입력은 최대 512개 조각 및 합계 4 MiB로 제한한다(처리 중 조각도 바이트 예산에 포함).
초과하면 분석용 조각만 거부하고 누락 조각/바이트를 표시한다. 기존 RX·로그·룰·브리지의
처리를 기다리게 하지 않는다. 누락, 연결 세대 변경, Clear와 분석 재시작 경계에서
조립 중인 프레임을 초기화하여 서로 다른 스트림의 조각을 합치지 않는다.
작업자 예외는 Protocol 상태와 기존 Health 오류 경로에 노출하며 종료 시 취소·회수한다.

## 누적 통계

RX/TX 분석 건수, CRC 정상/오류, 불완전 조각, 미해석 기능, Modbus 예외 응답을
작업자가 결과를 확정할 때 한 번만 집계한다. 탭 전환·스냅샷·오래된 행 만료로 재집계하거나
지우지 않는다. 시작 시각과 마지막 CRC 정상 프레임의 관측 시각도 표시한다.
최초 집계 기준은 창의 분석기 생성 시각이다. 관측 시각은 프레임이 시작된 입력 chunk의
시각을 보존하며, 같은 read 안의 실제 바이트별 선로 시각은 추정하지 않는다. 마지막 CRC
정상 시각은 지연 전달된 과거 데이터 때문에 역행하지 않도록 관측 시각의 최댓값을 쓴다.
`통계 초기화`는 이 카운터 및 누락/보관 만료 카운터를 0으로 돌리고 집계 시작을 갱신한다.
기존 목록은 남기며, 처리 대기 중이던 데이터는 이후 결과가 확정되면 새 집계에 포함된다.

CRC 미확인은 CRC 오류로 세지 않는다. CRC 정상은 의미 검증이나 요청 성공을 뜻하지 않는다.
불완전/미해석 조각의 실제 선로 프레임 수는 알 수 없으므로 RX/TX 숫자는 분석 결과 건수다.
여러 손상 프레임이 경계를 복원할 수 없는 한 조각으로 남으면 그 조각 하나를 불완전으로
집계한다. CRC 오류 수는 길이를 확정한 손상 후보만 집계하며 전체 선로 오류 수의 보장은 아니다.
분석 누락은 패킷 수가 아닌 거부한 입력 **청크/바이트** 수이고 정상 보관 만료와 별개다.

## 해석 범위와 경계의 의미

공개 Modbus V1.1b3 / Serial Line V1.02 규격을 기준으로 직접 구현했다.
일반적인 읽기/쓰기 기능 01–06, 0F, 10과 일부 표준 기능, 예외 응답을 인식한다.
RX의 단일 쓰기처럼 요청과 응답의 형식이 같은 경우 `RequestOrResponse`로 표시한다.
주소가 없는 읽기 응답은 `+0`, `+1`처럼 응답 내 오프셋을 보여주며 시작 주소나
제조사의 단위/배율/32비트 워드 순서를 추측하지 않는다. 자동 요청-응답 연계는 하지 않는다.
CRC가 잘못된 데이터에서는 레지스터 값을 확정하지 않는다.

어떤 USB read 경계나 기존 HEX 화면 한 줄도 RTU 프레임 경계로 단정하지 않는다.
최대 256바이트 버퍼와 기능별 길이/CRC를 사용해 분할 read 및 여러 프레임이 합쳐진
read를 처리한다. 잘못된 CRC 뒤의 정상 프레임은 제한된 범위에서 재동기화한다.
지원하지 않는 기능은 CRC가 일치하더라도 `Undecoded`이며 불완전 데이터와 구별한다.
알려진 전체 길이와 끝 경계가 일치하는 손상 후보는 본문 내부에서 우연히 CRC가 맞는
바이트열을 찾아 정상 요청으로 만들지 않고 그 후보의 CRC 오류로 표시한다. 짧은 요청과
더 긴 응답 후보의 CRC가 모두 맞으면 추가 바이트·끝 경계·뒤따르는 유효 프레임을 함께 본다.
형식을 확정할 수 없는 데이터는 50 ms 조립 대기 또는 버퍼 상한에서 제한된 조각으로
표시한다. 이 50 ms는 호스트 측 조립 대기이지 규격의 t1.5/t3.5 판정값이 아니다.
원본 단조 수신 시각과 native idle 완료 여부를 보존한다. native idle 완료이고 적용된
idle timeout이 설정된 baud/문자 크기의 t3.5 이상인 경우에는 조각 끝에서 조립을 마감한다.
19,200 bps 초과에서는 규격의 1.75 ms 기준을 사용한다. 더 짧은 timeout이나 단순 USB read
경계를 확정 프레임 경계로 취급하지 않는다. 이 메타데이터도 Windows 드라이버 관측 기준이다.
PC/USB 관측만으로 실제 선로의 문자 간격, 충돌, 규격 준수를 증명하지 않는다.

## 공개 상용 도구 조사와 독립 구현

2026-11-07에 다음 공개 문서의 기능 설명을 확인했다. 공개 문서로 확인되지 않은

다항식에서 코드로 생성한다. 표준의 알고리즘 설명과 공개 기능 설명을 바탕으로
코드와 UI를 독립적으로 작성했으며, 상용 도구와 동일 구현이라고 주장하지 않는다.

## 확인할 사용 흐름

1. 연결 후 Protocol에서 Modbus RTU 선택. 요청을 전송하지 않고 새 RX가 분석되는지 확인.
2. 정상 요청/응답, CRC 손상, 예외 02를 관측하고 Protocol 행 선택 시 상세를 확인.
3. Search 등 다른 탭에서 통신을 계속한 후 돌아와 새 결과와 기존 선택이 유지되는지 확인.
4. 파일 로그 OFF와 화면 Pause 상태에서도 Protocol 분석이 유지되는지 확인.
5. 10,000개 초과 시 오래된 항목만 만료되고 선택 항목 만료가 표시되는지 확인.
6. 사용 안 함 → 재활성화, Clear, 재연결에서 이전 조각이 새 프레임에 섞이지 않는지 확인.

## 엔진 단독 메모리·처리량 측정

검증용 Release 빌드의 별도 .NET 8 콘솔에서 CRC가 정상인 8바이트 요청으로 측정했다.
10,000개로 준비 후 200,000개를 추가 처리했으며, 최근 보관은 10,000개, 만료는 200,000개,
분석 누락과 입력 대기는 0이었다. 관측 시각 보존을 포함한 최종 코드의 이 PC 한 번 측정에서
경과 약 255 ms / CPU 약 266 ms, GC 후 관리 메모리 약 1.66 MB → 1.74 MB,
결과 보관 추정치 2.64 MB였다(10진 MB).
이는 엔진과 스냅샷 폴링의 합성 입력 측정이다. 실제 UART·드라이버·WinUI 목록/상세 표시의
비용, 잡음/모호한 입력의 처리량이나 다른 PC 성능을 보장하지 않는다.
