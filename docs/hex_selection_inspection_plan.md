# HEX 선택 영역 해석 개발 계획

- 작성일: 2026-10-28
- 상태: 보류. 현재는 계획만 기록하며 제품 코드 변경과 구현 검증은 시작하지 않는다.
- 구현 재개 조건: 사용자의 별도 구현 요청.
- 최우선 기준: 장시간 수신과 로그 화면의 응답성 유지.

## 확정한 표시 규칙

선택한 HEX payload가 완전한 1~4바이트일 때 기존 선택 툴팁에 BIN, DEC, ASCII를 추가한다. 상한은 4바이트로 고정한다.

```text
Len: 2 bytes · Δt: 12ms
BIN    10101011 11001101
DEC    171 205
ASCII  ··
```

- BIN: 바이트마다 8자리로 표시하고 선행 0을 유지한다. 최대 4바이트를 한 줄에 표시한다.
- DEC: 선택 순서대로 바이트별 unsigned 10진수(0~255)를 표시한다.
- ASCII: 0x20~0x7E는 해당 문자를 표시하고, 그 밖의 값은 `·`로 표시한다. 공백도 원래 순서와 개수를 유지한다.
- 5바이트 이상: 기존 길이·시간차 표시만 유지한다. 처음 4바이트 미리보기는 제공하지 않는다.
- 반쪽 HEX 바이트가 포함되거나 payload를 정확히 판별할 수 없는 선택: 해석을 생략한다. 빠진 자릿수를 추측하거나 선택을 자동 확장하지 않는다.
- timestamp, RX/TX 접두사, SYS 및 사용자 마커를 데이터로 오인하지 않는다.
- 화면 자동 줄바꿈, 접두사 숨김, 역방향 드래그에서도 선택한 payload 순서를 유지한다.
- 툴팁의 기존 화면 가장자리 보정과 테마 대응을 유지한다.

합친 정수, BE/LE, float, 전체 해석 패널, 우클릭 메뉴, 설정 옵션은 이번 계획의 범위에 포함하지 않는다.

## 성능 설계

4바이트 변환 자체보다 선택 문자열 생성, 보관 로그 탐색, 압축된 과거 행 접근의 비용을 먼저 관리한다.

1. 새 해석을 위해 `terminal.getSelection()`으로 전체 선택 문자열을 추가 생성하지 않는다. 선택 좌표를 먼저 확인하고 제한된 범위만 읽는다.
2. 최대 4바이트만 보관한다. 5번째 완전한 바이트가 확인되면 해석을 중단한다. 공백이나 메타데이터만 길게 선택한 경우에도 작업이 제한되도록 검사 문자·행 수에 별도 상한을 둔다. 정확한 상한은 기존 표시 형식과 화면 줄바꿈 검증 후 정한다.
3. 선택이 같고 대상 데이터가 유효하면 계산 결과를 재사용한다. 포인터 위치만 달라지면 툴팁 위치만 갱신한다. 캐시는 현재 선택 하나만 보관한다.
4. 기존 갱신 이벤트 합치기를 활용해 중복 계산을 막는다. 마우스를 놓는 최종 갱신에서도 해석용 읽기 상한을 우회하지 않는다.
5. 선택 변경, Clear, 모드 전환, 화면 재배치, 보관 로그 제거 시 오래된 결과나 예약 작업이 새 선택에 적용되지 않도록 무효화한다.
6. 해석은 WebView 내부의 화면 처리로 구현한다. 드래그마다 C#과 왕복하거나 RX 콜백, 파싱, 파일 기록 경로에 작업을 추가하지 않는다.

## 구현 전에 확인할 기존 경로

현재 `SerialMonitor.WinUI/Assets/xterm/index.html`의 선택 처리에는 다음 점검 사항이 있다.

- 길이 계산이 전체 `terminal.getSelection()` 문자열을 사용한다. 드래그 중 행 수 제한은 있지만 마우스를 놓는 강제 갱신 경로에서는 이 제한을 우회한다.
- 시간차 계산은 캐시가 없으면 전체 보관 행의 논리 줄 인덱스를 재구축할 수 있다. 수신 중 캐시 무효화도 발생한다.
- 과거 로그의 텍스트를 넓게 읽으면 압축 행 해제와 캐시 퇴출 비용이 발생할 수 있다.

구현을 재개하면 이 경로의 기준 성능부터 측정한다. 새 해석에 기존 전체 선택 스캔을 그대로 재사용하지 않는다. 기존 길이·시간차 경로의 개선이 필요하면 신규 해석과 구분해 변경 범위를 정리한다. 긴 선택의 정확한 길이를 유지하려면 취소 가능한 분할 계산을 검토하며, 드래그 종료 시 전체 데이터를 동기로 읽는 우회는 피한다.

## 구현 및 검증 순서

1. 기존 선택 처리의 시간, 읽는 문자·행 수, 메모리 사용을 측정한다.
2. 화면과 분리한 작은 해석 함수와 읽기 상한을 검증한다.
3. 기존 툴팁에 연결하고 캐시·무효화·이벤트 합치기를 적용한다.
4. 아래 기능 및 성능 회귀를 확인한 뒤 결과를 보고한다.

### 기능 검증

- 1, 2, 3, 4바이트의 정확한 BIN/DEC/ASCII와 5바이트부터의 해석 생략.
- `00`, `20`, `41`, `7E`, `7F`, `FF`, 선행 0, ASCII 공백 및 비출력 문자.
- HEX 반쪽 선택, 접두사/시간 포함, 접두사 숨김, 마커, 양방향 드래그, 자동 줄바꿈.
- 수신 중 선택 유지, Clear, 모드 전환, resize/reflow, 오래된 로그 제거.

### 성능 검증

- 기존 `scripts/test_xterm_hex_interactions.cjs`의 10만 로그 행, 전체 선택, 큰 단일 HEX 패킷 시나리오를 활용한다.
- 수신 중 반복 드래그와 마우스를 놓는 순간을 별도로 측정한다.
- 긴 선택에서도 새 해석기가 읽는 문자·행 수와 보관 바이트 수가 고정 상한을 넘지 않는지 검증한다.
- 새 해석으로 전체 선택 문자열 생성, 압축 해제 행 수, 메모리 사용이 선택 크기에 비례해 늘지 않는지 확인한다.
- UI 작업 시간과 로그 append 대기 상태를 기준 성능과 비교한다. 프레임 지연이나 긴 동기 작업이 생기면 해당 경로를 보완한 뒤 다시 검증한다.

이 문서 작성 시점에는 제품 코드를 수정하거나 테스트를 실행하지 않았다.
