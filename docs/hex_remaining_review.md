# 남은 HEX 지연 경로 검토 — 2026-09-11

사용자 요청에 따라 회귀 위험이 큰 최적화는 적용하지 않았다. 이번 단계에서 제품 코드는 추가 변경하지 않았으며, 재실행 가능한 브라우저 시험과 결과만 추가했다. 이전 단계의 HEX 포맷/UI 배치 개선은 유지한다.

## 실제 화면 엔진 측정

`scripts/test_xterm_hex_interactions.cjs`는 개인 브라우저 프로필과 분리된 headless Edge에서 현재 번들 xterm 및 페이지 함수를 실행한다. 초기 viewport 1400×850, 32바이트 HEX 로그 100,000개, scrollback 400,000행 조건이다. 이후 폭을 60열로 바꿔 줄바꿈을 재계산한다. 실제 WinUI/WebView2 호스트와 COM 장치를 포함한 측정은 아니다.

| 작업 | 관찰 시간 | 정확성 결과 |
|---|---:|---|
| 캐시 없이 두 행의 시간 차이 조회 | 4.8ms | 1ms로 정확 |
| 캐시가 있는 동일 조회 | 측정 해상도상 0ms | 동일 |
| 10만 행 전체 선택 문자열 추출 | 1,064ms | 10,200,000문자 |
| 선택 문자열의 HEX 바이트 집계 | 188.5ms | 3,200,000바이트로 정확 |
| 60열로 폭 변경, 줄바꿈 재계산 | 1,528ms | 논리 행 100,000개 유지 |
| 폭 변경 후 선택 집계/시간 차이 | 시간 미기록 | 3,200,000바이트 / 1ms 유지 |
| 단일 64KiB HEX 패킷 선택·집계 | 18.5ms | 65,536바이트로 정확 |

전체 선택 문자열 추출과 집계는 같은 화면 스레드에서 동기 실행되므로, 합계 약 1.25초의 긴 작업을 설명할 수 있다. 이 수치는 대량 선택 조건이며 작은 선택에 그대로 적용되지 않는다. 전체 이력 탐색의 4.8ms는 이번 10만 행 fixture의 단발 값이고, 수신마다 캐시가 무효화되는 드래그 조건에서는 반복 비용이 생긴다.

## 복구·압축·장기 이력 검증

- JS 단위/차등 시험 13개 통과: 압축 왕복, 원본 xterm과 비교한 rollover/Unicode/reflow/편집/화면 전환/clear, 오래된 이력 복사 시 압축 해제 캐시 한도, 압축 오류 보고, write/복구 실패 시 큐 해제 등.
- 이력 시험 2개 통과: 메타데이터 ID/시간 보존과 100만 행을 유지한 총 300만 행 쓰기.
- 각 100만 행 pass 후 live JS+cell 메모리는 358.4 / 366.0 / 371.1MiB. RSS는 626.2 / 872.4 / 907.0MiB로 증가했다. 살아 있는 객체는 제한 내에 있었지만 프로세스 RSS까지 고정된다는 뜻은 아니다. 이 시험은 일반 텍스트 fixture이며 대형 HEX raw payload의 .NET 메모리는 포함하지 않는다.
- 기존 실제 브라우저 시험 3개 통과: 10만 행의 선택/스크롤/리사이즈, 100만 행 복구 및 이후 live 로그, 진행률 표시.
- 복구 시험은 약 15.93초 소요. 마지막 live 로그 `live 499`, 대기열 0, 쓰기 비활성, 임시 queue chunk 참조 0, 메타데이터 1,000,000개, 수집된 페이지 오류 없음.
- 신규 HEX 브라우저 시험도 통과. 기존 C# 테스트 결과를 이번 단계에서 새로 실행한 것으로 집계하지 않는다.

## 보류한 변경과 이유

1. **선택/집계 비동기화:** 긴 작업은 재현했지만, 수신·스크롤·선택 변경 중 오래된 결과가 뒤늦게 표시될 수 있다. 취소와 선택 버전 검증까지 함께 설계해야 하므로 단순히 타이머로 나누지 않았다.
2. **논리 행 인덱스 증분 갱신:** reflow, 이력 앞부분 잘림, 부분 RX, clear/restore가 모두 인덱스에 영향을 준다. 잘못 바꾸면 시간 차이와 검색 위치가 어긋날 수 있어 미변경.
3. **리사이즈 최적화/재배치 제한:** 현재 선택 바이트 수와 시간 매핑은 검증 조건에서 맞는다. 줄바꿈을 생략하거나 미루면 표시 폭과 위치 매핑이 달라질 수 있어 미변경.
4. **단일 대형 전송 조각 추가 분할:** 현재 live 전송 분할은 줄바꿈 경계를 우선하므로 긴 한 줄은 256Ki 문자 기준을 넘을 수 있다. ANSI/OSC 파서 상태, 순서, write 완료 확인, 부분 RX 표시까지 검증해야 해 미변경. 이전 단계의 UI 비용 예산은 단일 큰 항목 자체를 분할하지 않는다.
5. **보관 메모리에 새로운 바이트 한도 도입:** 현재 행/항목 수가 같아도 raw bytes와 HEX 텍스트 크기는 다르다. byte cap 도입은 화면 이력 폐기와 검색 가능 범위를 바꾸므로 임의로 추가하지 않았다. 64Mi 문자 snapshot 상수는 초기 할당량 제한이지 최종 snapshot 크기 제한이 아니다.
6. **검색 snapshot을 백그라운드로 이동:** 검색 계산은 이미 Task.Run으로 분리되고 취소/결과 버전 검증이 있다. 하지만 `GetVisibleSearchContentSnapshot`은 UI에서 전체 목록을 만들고 active partial 문자열을 확정한다. 이를 그대로 다른 스레드로 옮기면 수정 중인 UI 이력과 경쟁하게 되므로 미변경. snapshot 캡처/검색 계산 시간은 기존 진단 값으로 구분 가능하다.

## 결론

추가로 확인한 큰 지연은 대량 선택과 폭 변경/전체 복구에 집중되어 있다. 이번 검증에서 내용 손상은 발견하지 못했지만 모든 드래그·수신 동시 실행을 보장하는 것은 아니다. 동작을 보존할 자신이 없는 최적화는 보류했다. timeout, 패킷 경계, 검색/선택 및 보관 정책은 이번 단계에서 변경하지 않았다.
