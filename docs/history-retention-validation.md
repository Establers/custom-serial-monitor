# 장시간 로그 보관 변경 검토 및 검증 — 2026-09-08

## 판단

기존 큐 통합·문자열 공유·메타데이터 순환 버퍼는 적절하다. 그러나 xterm의 scrollback만 100만으로 늘리고 수 GB 사용을 불가피하다고 보는 것은 충분한 해결이 아니다. 배포 중인 xterm은 문자·전경색·배경색을 각 32비트로, 빈 칸을 포함한 모든 열에 보관한다. 120열 × 100만 행의 셀 배열만 약 1,373MiB이며 객체 등의 비용이 추가된다. 이는 로그 텍스트 자체의 필수 비용이 아니다.

MobaXterm에도 ScrollbackLines 한도가 있다([제조사 문서](https://blog.mobatek.net/post/mobaxterm-configuration-settings/)). MobaXterm/PuTTY 프로세스를 직접 측정하지 않았으므로 몇 배 효율적인지 비교하지 않는다.

## 반영한 내용

- 기본값·최대 보관량 1,000,000줄을 유지한다. 기존 프로필 값은 유지하므로 Settings → Line scrollback → 1000000을 선택해야 한다.
- C# 큐 통합과 문자열 공유를 유지하고, 사용자가 보관 한도를 줄일 때 큰 큐 배열도 반환한다.
- compact-scrollback.js에서 오래된 화면 행의 셀을 메모리 안에서 무손실 압축한다. 문자/색상 평면별 반복 길이·XOR 차이값을 저장하며, 압축에 불리한 데이터는 원래 바이트 크기+1 이내로 저장한다. 한글, 결합 문자, 넓은 문자, 확장 속성은 유지한다.
- 현재 화면과 최근 256행은 원래 형태로 둔다. 과거 행은 읽을 때 해제하며 해제된 셀 캐시는 최대 512행이다. 오래된 이력을 검색·복사한 후 전체 이력이 해제된 상태로 남지 않는다.
- 압축 작업은 한 번에 최대 2,048행, 약 4ms 단위로 나눈다(시간 확인 간격 32행). 매 수신마다 전체 이력을 재탐색하지 않으며, 한도 도달 후 삭제량만큼 진행 위치를 조정한다.
- 백그라운드 압축 오류를 포착해 기존 UI 오류 집계로 전달한다. 압축에 실패한 원래 행을 먼저 삭제하지 않는다.
- 자동 저장이나 임시 디스크 로그는 추가하지 않았다.

## 측정

120열 × 30행, 최근 100만 행을 유지하며 300만 행을 입력했다. 약 50문자의 서로 다른 packet/temperature/voltage/status 행을 1,000개씩 입력한다. 같은 배포 xterm에 압축만 켜고 끈 비교이며 별도 Node 프로세스로 측정했다.

| 구간 | 원래 xterm 보관 메모리 | 압축 후 보관 메모리 | 원래 처리 시간 | 압축 후 처리 시간 |
|---|---:|---:|---:|---:|
| 최초 100만 행 | 1,731.4MiB | 355.7MiB | 12.82초 | 11.44초 |
| 다음 100만 행으로 교체 | 1,731.7MiB | 365.7MiB | 14.50초 | 11.63초 |
| 다음 100만 행으로 교체 | 1,731.5MiB | 355.9MiB | 13.16초 | 11.17초 |

보관 메모리는 GC 후 heapUsed + arrayBuffers이다. 화면 셀 보관 비용은 약 **79% 감소**했고 한도 도달 후 계속 증가하지 않았다. 압축 후 Node RSS는 시험에 따라 약 639~913MiB, 원래 xterm RSS는 약 2,020~2,133MiB였다. RSS는 런타임이 확보한 여유 메모리·할당기 비용 등도 포함한다. 처리 시간은 프레임 시간 보장이 아니다.

C# 이력은 원본 바이트·텍스트·검색/표시 문자열을 별도로 보관한다. 고유 문자열과 원본 바이트를 포함한 별도 300만 줄 시험에서 보관 증가분은 585.9 → 585.9 → 585.9MiB, 100만 줄당 처리는 1.82 → 1.71 → 1.66초였다. C#과 화면 엔진 시험은 별도 프로세스이므로 합산을 전체 앱의 실제 RSS로 제시하지 않는다. 화면 메모리 시험에는 DOM 렌더러와 OSC 메타데이터가 포함되지 않는다.

## 검증 결과

- WinUI 관련 C# 테스트 349개, Core 테스트 35개 통과.
- JS 큐·압축 기능 테스트 12개, 100만 행 이력/메타데이터 테스트 2개 통과.
- 원래 xterm과 압축 xterm의 모든 셀·속성·줄바꿈 상태를 비교했다. 한글/중문/이모지/결합 문자, ANSI 색상·밑줄, 반복적인 창 좁히기/넓히기, 삽입/삭제, alternate screen, 용량 변경, clear/reset, 한도 이후 교체를 포함한다.
- 타이머에서 압축 실패를 발생시켜 오류가 한 번 보고되고 원래 행과 후속 수신이 유지되는지 확인했다.
- 실제 headless Edge에서 배포 HTML을 열고 OSC 메타데이터와 색상·한글을 포함한 11만 줄을 입력했다. 10만 행+화면 행 유지, 오래된 행 스크롤/선택, 창 크기 변경을 검증했다. 압축 행 99,544개, 페이지 오류 0개였다. WinUI/WebView2 프로세스 전체 시험과는 구분한다.
- Release x64 빌드 오류 0개, 경고 0개.

## 남는 한계와 유지보수

**모든 PC에서 렉이나 메모리 부족이 전혀 없다는 보장은 하지 않는다.** 원본 바이트와 검색 문자열까지 필요하므로 100만 줄은 여전히 상당한 메모리를 쓴다. 긴 줄과 고유한 색상이 많은 데이터는 압축 효율이 낮다. 행 수 한도는 유지하며 무제한 보관은 제공하지 않는다.

표시 방식 변경에 따른 전체 재구성, 대량 복사·검색, 창 너비 변경에 따른 줄 재배치는 여전히 이력 크기에 비례한 작업이다. 압축은 전체 가상화나 디스크 기반 이력을 구현한 것이 아니다. 수일·수주 실장비 연결, 절전·복귀, 실제 WebView2의 장기 프레임 지연은 아직 측정하지 않았다.

xterm의 한도는 화면 행이므로 긴 한 줄이 접히면 스크롤로 볼 수 있는 원본 줄 수는 줄어든다. C# 보관 한도는 수신 기록 단위이며 partial RX 조각·필터에 따라 표시 줄 수와 다를 수 있다.

압축 어댑터는 배포된 xterm의 내부 BufferLine 구조에 의존한다. 원본 xterm.js나 전역 프로토타입을 수정하지 않고 과거 행만 같은 인터페이스의 압축 객체로 교체한다. xterm SHA-256을 테스트에 고정했다. 라이브러리 교체 시 어댑터 검토와 차등·메모리·브라우저 테스트를 반드시 다시 수행해야 한다.
