# 장시간 로그 보관 변경 검토 및 검증 — 2026-09-08

## 판단

기존 큐 통합·문자열 공유·메타데이터 순환 버퍼는 적절하다. 그러나 xterm의 scrollback만 100만으로 늘리고 수 GB 사용을 불가피하다고 보는 것은 충분한 해결이 아니다. 배포 중인 xterm은 문자·전경색·배경색을 각 32비트로, 빈 칸을 포함한 모든 열에 보관한다. 120열 × 100만 행의 셀 배열만 약 1,373MiB이며 객체 등의 비용이 추가된다. 이는 로그 텍스트 자체의 필수 비용이 아니다.

MobaXterm에도 ScrollbackLines 한도가 있다([제조사 문서](https://blog.mobatek.net/post/mobaxterm-configuration-settings/)). MobaXterm/PuTTY 프로세스를 직접 측정하지 않았으므로 몇 배 효율적인지 비교하지 않는다.

## 반영한 내용

- 기본값·최대 보관량 1,000,000줄을 유지한다. 기존 프로필 값은 유지하므로 Settings → Line scrollback → 1000000을 선택해야 한다.
- C# 큐 통합과 문자열 공유를 유지하고, 사용자가 보관 한도를 줄일 때 큰 큐 배열도 반환한다.
- compact-scrollback.js에서 오래된 화면 행의 셀을 메모리 안에서 무손실 압축한다. 문자/색상 평면별 반복 길이·XOR 차이값을 저장하며, 압축에 불리한 데이터는 원래 바이트 크기+1 이내로 저장한다. 한글, 결합 문자, 넓은 문자, 확장 속성은 유지한다.
- 현재 화면과 최근 256행은 원래 형태로 둔다. 과거 행은 읽을 때 해제하며 해제된 셀 캐시는 최대 512행이다. 오래된 이력을 검색·복사한 후 전체 이력이 해제된 상태로 남지 않는다.
- 압축 작업은 한 번에 최대 2,048행, 약 4ms 단위로 나눈다(시간 확인 간격 32행). 매 수신마다 전체 이력을 재탐색하지 않으며, 한도 도달 후 삭제량만큼 진행 위치를 조정한다.
- 백그라운드 압축 오류를 포착해 기존 UI 오류 집계로 전달한다. 압축에 실패한 원래 행을 먼저 삭제하지 않는다.
- 자동 저장이나 임시 디스크 로그는 추가하지 않았다.

## 화면 메모리 제한

- Settings → UI / xterm의 `Log MiB`에서 보관 데이터 예산을 64–2048MiB로 조절한다. 기본값은 256MiB이며 프로필에 저장한다. 기존 프로필도 항목이 없으면 256MiB를 사용한다.
- 문자 제한은 64Mi 문자다. Max Lines·보관 데이터 예산·문자 제한 중 먼저 닿는 한도에 따라 오래된 화면 이력이 제거된다. 표시·검색 문자열, xterm 렌더링과 다른 서비스가 사용하는 메모리 때문에 앱 전체 사용량은 예산보다 크다.
- 한도 도달 시 여유분은 25%에서 1%로 줄였다. 새 레코드 공간과 완전한 화면 줄 경계를 확보하기 위해 추가로 제거될 수 있다. 일반 정리는 앞부분의 행과 메타데이터만 제거하며 전체 이력을 다시 전송하지 않는다.
- 예산을 낮추면 즉시 앞부분을 정리하고, 높이면 이후 수신분부터 보관 여유가 늘어난다. 이미 제거된 화면 이력은 복구하지 않는다. 파일 로그와 룰·시퀀스의 원본 데이터 경로는 독립적이다.

Node 회귀는 `node --test scripts/test_xterm_retention.cjs scripts/test_log_navigation_terminal.cjs scripts/test_xterm_queue.mjs`로 실행한다. 브라우저나 데스크톱을 조작하지 않고 배포된 xterm 파서와 큐를 사용해 앞부분 제거, 남은 셀 재사용·제거된 참조 해제, 커서·줄바꿈 없는 수신, 전송 중 분리된 정리 경계, 너비 재배치 및 초기화 중 취소를 검증한다. 설정 기본값·저장/복원·범위 검증과 C# 메모리·문자 경계, 파일 원본 보존은 관련 .NET 회귀에서 확인한다.

## 부분 RX 문자열 공유 검증 — 2026-11-13

- 한 조각으로 끝나는 RX 줄은 기존 표시·검색 문자열을 그대로 보관하고, 이어지는 조각이 올 때만 `StringBuilder`를 만든다.
- 표시와 검색 내용이 같은 동안에는 버퍼와 완성 문자열을 공유한다. ANSI 색상·괄호 강조로 표시가 달라지면 먼저 버퍼를 분리한다. 룰이 뒤늦게 색상을 적용하거나 기본 색상으로 되돌려도 검색 문자열에 ANSI가 들어가지 않는다.
- 메모리 예산을 낮출 때 레코드 제거 후 남는 큐의 큰 여유 배열도 반환한다. 보관 줄 수를 줄일 때와 같은 경로를 사용하며, 자동 정리마다 배열 전체를 재할당하지 않는다.
- 255자 로그 20,000줄을 부분 RX+줄 종료 레코드로 입력한 별도 검사에서 화면 투영의 관리 메모리 증가분은 **30,006,200 → 18,002,168바이트(약 40% 감소)**, 해당 동기 경로의 스레드 할당량은 **106,163,584 → 56,243,568바이트(약 47% 감소)**였다.
- 원본 레코드를 먼저 만든 뒤 GC 후 추가 보관량을 측정했다. 이 입력에는 raw byte 배열이 없으며, xterm·DOM·프로세스 RSS·실물 UART 장기 시험은 포함하지 않는다. 전체 앱 메모리 감소율이 아니다.
- 재현: Release x64 빌드 후 `dotnet test SerialMonitor.WinUI.Tests/SerialMonitor.WinUI.Tests.csproj -c Release -p:Platform=x64 --no-build --filter FullyQualifiedName~PartialRxProjectionMemoryTests --logger "console;verbosity=detailed"`.
- `LogRetentionProjectionRegressionTests`는 Terminal/HEX에서 여러 고정 난수 입력으로 부분 RX·TX·시스템 로그·필터·보관 줄 수·타임스탬프 변경을 섞어, 화면에 보낸 증분과 현재 보관 스냅샷이 일치하는지 확인한다. Node 검사에는 압축 ON/OFF 각각 120회 삭제·너비/높이 변경·한글/이모지/결합 문자·탭 입력을 추가했다.

## 모드버스·메모리 통합 검사

`ModbusMemoryIntegrationTests`는 GUI나 실물 포트를 열지 않고 모의 시리얼 드라이버와 실제 Modbus 엔진·로그 파이프라인·파일 writer·화면 로그 모델을 연결한다.

- 분할된 RTU 응답을 반복 수신하면서 작은 화면 메모리 한도로 오래된 이력을 제거한다. 폴링 중 보관 줄 수와 메모리 예산도 변경한다.
- 정리 후에도 마지막 레지스터 값·정상 종료·연결 소유권 해제를 확인하고, 디스크에 저장된 TX/RX를 바이트로 복원해 각각 원본 SHA-256과 비교한다. 화면 제거와 파일 writer의 누락을 구분한다.
- 메모리 예산과 Modbus 대상 설정을 함께 저장·복원하고, 시퀀스 저장 경로를 거쳐도 두 설정이 유지되는지 확인한다.
- 잘못된 Modbus 표시 형식을 읽고 다시 저장하는 경우에도 화면 메모리 예산·보관 줄 수·통신 대상이 초기화되지 않는지 확인한다.

개별 실행은 Release x64 빌드 후 `dotnet test SerialMonitor.WinUI.Tests/SerialMonitor.WinUI.Tests.csproj -c Release -p:Platform=x64 --no-build --filter FullyQualifiedName~ModbusMemoryIntegrationTests`를 사용한다. 최종 통합 검증은 Modbus 후속 수정과 메모리 변경이 함께 들어간 HEAD에서 솔루션 빌드·전체 C# 회귀·Node 터미널 회귀로 수행한다. GUI 상호작용과 실물 UART 장기 운전은 별도 수동 검증 범위다.

2026-11-13에는 `f055366`(Modbus 구현 `b42fe99`, 메모리 변경 `ec7a56c`·`60c89fa` 포함)을 기준으로 루트 Release 솔루션 빌드가 경고·오류 0으로 통과했고, 교차 검사 4개를 다시 실행해 모두 통과했다. 같은 최종 소스의 전체 검사 TRX를 재확인한 결과 Core 668개·WinUI 1,963개가 통과했고 장치 조건부 17개는 제외됐다. 전체 결과 안에도 교차 검사 4개가 포함되어 있다. 본 작업의 재실행 결과는 `SerialMonitor.WinUI.Tests/TestResults/modbus-memory-cross-final.trx`에 기록한다. Node 터미널 회귀 30개도 통과했으며, Modbus 후속 수정에서 해당 JS·검사 소스가 바뀌지 않았음을 확인했다.

## 측정

120열 × 30행, 최근 100만 행을 유지하며 300만 행을 입력했다. 약 50문자의 서로 다른 packet/temperature/voltage/status 행을 1,000개씩 입력한다. 같은 배포 xterm에 압축만 켜고 끈 비교이며 별도 Node 프로세스로 측정했다.

| 구간 | 원래 xterm 보관 메모리 | 압축 후 보관 메모리 | 원래 처리 시간 | 압축 후 처리 시간 |
|---|---:|---:|---:|---:|
| 최초 100만 행 | 1,731.4MiB | 355.7MiB | 12.82초 | 11.44초 |
| 다음 100만 행으로 교체 | 1,731.7MiB | 365.7MiB | 14.50초 | 11.63초 |
| 다음 100만 행으로 교체 | 1,731.5MiB | 355.9MiB | 13.16초 | 11.17초 |

보관 메모리는 GC 후 heapUsed + arrayBuffers이다. 화면 셀 보관 비용은 약 **79% 감소**했고 한도 도달 후 계속 증가하지 않았다. 압축 후 Node RSS는 시험에 따라 약 639~913MiB, 원래 xterm RSS는 약 2,020~2,133MiB였다. RSS는 런타임이 확보한 여유 메모리·할당기 비용 등도 포함한다. 처리 시간은 프레임 시간 보장이 아니다.

C# 이력은 원본 바이트·텍스트·검색/표시 문자열을 별도로 보관한다. 고유 문자열과 원본 바이트를 포함한 별도 300만 줄 시험에서 보관 증가분은 585.9 → 585.9 → 585.9MiB, 100만 줄당 처리는 1.82 → 1.71 → 1.66초였다. C#과 화면 엔진 시험은 별도 프로세스이므로 합산을 전체 앱의 실제 RSS로 제시하지 않는다. 화면 메모리 시험에는 DOM 렌더러와 OSC 메타데이터가 포함되지 않는다.

## 검증 결과

- WinUI 관련 C# 테스트 349개, Core 테스트 35개 통과.
- JS 큐·압축 기능 테스트 12개, 100만 행 이력/메타데이터 테스트 2개 통과.
- 원래 xterm과 압축 xterm의 모든 셀·속성·줄바꿈 상태를 비교했다. 한글/중문/이모지/결합 문자, ANSI 색상·밑줄, 반복적인 창 좁히기/넓히기, 삽입/삭제, alternate screen, 용량 변경, clear/reset, 한도 이후 교체를 포함한다.
- 타이머에서 압축 실패를 발생시켜 오류가 한 번 보고되고 원래 행과 후속 수신이 유지되는지 확인했다.
- 실제 headless Edge에서 배포 HTML을 열고 OSC 메타데이터와 색상·한글을 포함한 11만 줄을 입력했다. 10만 행+화면 행 유지, 오래된 행 스크롤/선택, 창 크기 변경을 검증했다. 압축 행 99,544개, 페이지 오류 0개였다. WinUI/WebView2 프로세스 전체 시험과는 구분한다.
- Release x64 빌드 오류 0개, 경고 0개.

## 남는 한계와 유지보수

**모든 PC에서 렉이나 메모리 부족이 전혀 없다는 보장은 하지 않는다.** 원본 바이트와 검색 문자열까지 필요하므로 100만 줄은 여전히 상당한 메모리를 쓴다. 긴 줄과 고유한 색상이 많은 데이터는 압축 효율이 낮다. 행 수 한도는 유지하며 무제한 보관은 제공하지 않는다.

표시 방식 변경에 따른 전체 재구성, 대량 복사·검색, 창 너비 변경에 따른 줄 재배치는 여전히 이력 크기에 비례한 작업이다. 압축은 전체 가상화나 디스크 기반 이력을 구현한 것이 아니다. 수일·수주 실장비 연결, 절전·복귀, 실제 WebView2의 장기 프레임 지연은 아직 측정하지 않았다.

xterm의 한도는 화면 행이므로 긴 한 줄이 접히면 스크롤로 볼 수 있는 원본 줄 수는 줄어든다. C# 보관 한도는 수신 기록 단위이며 partial RX 조각·필터에 따라 표시 줄 수와 다를 수 있다.

압축 어댑터는 배포된 xterm의 내부 BufferLine 구조에 의존한다. 원본 xterm.js나 전역 프로토타입을 수정하지 않고 과거 행만 같은 인터페이스의 압축 객체로 교체한다. xterm SHA-256을 테스트에 고정했다. 라이브러리 교체 시 어댑터 검토와 차등·메모리·브라우저 테스트를 반드시 다시 수행해야 한다.
