# HEX 지연 후보와 적용한 개선 — 2026-09-11

후속 검사: [남은 HEX 지연 경로 검토](hex_remaining_review.md)에 실제 화면 엔진의 선택/리사이즈/복구 측정과 위험 때문에 보류한 변경을 기록했다.

## 변경 요약

HEX 포맷의 바이트별 문자열 할당, 첫 partial 조각의 중복 변환, UI 배치의 데이터 크기 제한 누락을 수정했다. timeout 값·판정·수신 시각·64KiB partial 출력 시점·패킷 종료자 생성 코드는 변경하지 않았다. 앞선 설정 미적용 검토의 연결 스냅샷/동일 값 Set 문제도 이번 UI 성능 수정에 포함하지 않았다.

| 항목 | 지연이 나타날 수 있는 조건 | 확인 수준 | 이번 처리 |
|---|---|---|---|
| 바이트마다 `ToString("X2")` 문자열 생성 | 큰 HEX 패킷, 연속 수신 | 코드 및 할당량 측정 확인 | 배열은 최종 문자열에 직접 기록, span은 두 개의 큰 문자열만 생성 |
| 첫 partial 조각 중복 변환 | HEX 그룹 시작마다 길이 계산과 표시 문자열 생성 | 코드 확인 | 이미 만든 payload 문자열을 다음 포맷 단계에 전달 |
| 40/400항목을 크기 제한 없이 UI에서 가공 | 긴 패킷 또는 밀린 로그를 따라잡을 때 | 배치 경로 및 부하 측정 확인 | 기존 32Ki 문자 예산을 실제 배치에 적용 |
| 단일 초대형 조각의 UI 처리 | native에서 큰 청크가 전달되거나 큰 로그 항목이 생성됨 | 구조상 잔여 비용 | 항목 하나는 그대로 처리해 진행을 보장. 추가 분할은 하지 않음 |
| 드래그 선택 시 전체 이력 재탐색 | 이력이 많고 수신 중 선택을 움직일 때 | 코드상 후보, 브라우저 실측 미수행 | 미변경. 논리 행 인덱스 증분 갱신 또는 선택 주변 탐색이 별도 과제 |
| 대량 선택 해제 시 전체 선택 문자열 추출 | 강제 힌트 갱신으로 2,000행 제한을 우회하는 경우 | 코드상 후보 | 미변경. 비동기/분할 집계 필요 |
| 긴 줄의 렌더링·검색·리사이즈 및 이력 압축 해제 | 장기 기록 후 검색/스크롤/창 크기 변경 | 조건부 후보 | 미변경. WebView 성능 추적으로 구간별 비용 확인 필요 |
| 큐 및 화면 이력의 항목 크기 편차 | 큰 raw payload와 HEX 문자열이 많이 보관됨 | 항목 수 제한 코드 확인 | UI 순간 처리량은 축소. 전체 보관 메모리의 바이트 한도는 별도 과제 |
| timeout까지 기다리는 정상 그룹 누적 | timeout보다 짧은 간격의 연속 수신 | 기존 프레이밍 동작 | 의도대로 보존. 성능 수정으로 timeout이나 partial 출력 시점을 바꾸지 않음 |

## 구현상 보존 조건과 한계

- `HexFormatter`는 대문자 두 자리, 바이트 사이 공백 하나, 마지막 공백 없음, null/빈 배열의 빈 문자열을 유지한다. 모든 바이트 값과 64KiB 초과 입력을 검증했다.
- `DisplayText`가 임의의 preview일 수도 있으므로 무조건 재사용하지 않는다. 원본 바이트를 기준으로 화면을 만드는 의미를 보존하고, 같은 포맷 작업 내부에서만 문자열을 재사용한다.
- UI 예산은 예상 문자 수 기준의 soft limit이다. 현재 항목을 통째로 넣은 뒤 한도를 넘으면 다음 tick으로 넘긴다. 단일 대형 항목을 버리거나 나누지 않으며, 종료자 및 순서를 변경하지 않는다.
- 64KiB HEX 조각 400개가 밀려 있어도 같은 크기의 조각은 한 tick에 하나만 처리한다. 작은 항목들은 기존 40개/400개 개수 제한 내에서 계속 묶는다.
- 터미널에서는 텍스트 길이를, HEX RX에서는 raw 바이트 수의 3배를 비용으로 계산한다. 타임스탬프/접두사 여유 64자를 추가한다.
- 화면 따라잡기 처리량이 낮아질 수 있다. 기존 10,000항목 큐 및 오래된 UI 항목 폐기 정책은 그대로이므로 과부하가 지속되면 UI drop 카운터 확인이 필요하다. 파일 저장 및 이벤트 처리는 이 UI 예산의 대상이 아니다.

## 동일 조건 비교 측정

별도 .NET 8 Release 콘솔에서 64KiB ASCII 바이트의 partial RX 조각을 AddRange에 전달했다. 수정 전 LogViewModel은 Git HEAD 소스, 수정 후는 작업 디렉터리 소스이다. 각각 6회 중 첫 실행을 제외한 5회의 중앙값을 기록했다. 입력 배치 생성은 측정 밖이다. WebView, 실제 COM 장치 및 UI dispatcher는 제외했다.

| HEX 조각 수 | 수정 전 중앙값 | 수정 후 중앙값 | 수정 전 스레드 할당량 | 수정 후 스레드 할당량 |
|---:|---:|---:|---:|---:|
| 1 | 3.94ms | 0.55ms | 7.38MiB | 2.25MiB |
| 40 | 86.90ms | 17.81ms | 173.15MiB | 75.40MiB |
| 400 | 629.36ms | 131.27ms | 1,703.29MiB | 750.52MiB |

40개 조건의 UI 가공 시간은 약 80%, 할당량은 약 56% 감소했다. 이는 해당 대형 배치 조건의 측정값이며 실제 사용자 렉이 같은 비율로 줄었다는 뜻은 아니다. 벽시계 시간은 실행 환경에 따라 흔들리며, 할당량은 누적 생성량으로 상주 메모리가 아니다. 표는 새 dispatcher 제한을 제외했으므로 실제 UI에서는 동일한 400개 대형 조각을 한 tick에 가공하지 않는다.

## 검증

- WinUI 전체 테스트 396개 통과.
- Core 전체 테스트 35개 통과.
- HEX 포맷 5개 및 UI 비용 예산 4개 테스트 추가.
- 기존 패킷 경계/바이트 보존/출력/검색·필터/파일 저장 테스트와 추가 live timeout 테스트 포함.
- com0com 및 실제 장치 테스트에는 환경변수로 opt-in하는 테스트가 있으며 이번 실제 장치 검증은 수행하지 않았다. 테스트 러너의 통과 수를 하드웨어 실행 수로 해석해서는 안 된다.
- LogPipeline, SerialService, IdleGapBoundaryDetector, SerialReadTimingPolicy에 diff 없음. MainViewModel 변경은 UI dispatcher 생성 인자에 한정된다.
- `git diff --check` 통과. 별도 앱 실행 상태의 화면 및 장기 수신 부하 검증은 아직 하지 않았다.
