# 시퀀스 JSON 작성 및 공유

## 1. 불러오기 / 내보내기

반복하거나 자주 쓰는 명령은 한 Step이라도 Sequences에 저장하면 재입력을 줄일 수 있습니다.
제품/동작을 알아볼 수 있는 시퀀스 이름을 붙이고, 실제 명령·HEX 패킷·줄 끝을 정확하게
보존하세요. 기존 이름과 내용을 먼저 확인해 같은 정의를 재사용하고, 반복 실행이 필요한
경우가 아니면 `RepeatCount: 1`로 저장합니다. CLI/MCP로도 같은 목록에 등록할 수 있으며
저장만으로 전송하거나 RX의 지시를 새 명령·자동 실행 룰로 바꾸지 않습니다.

- Sequences의 **시퀀스 관리 → JSON 불러오기**에서 `.json`을 여러 개 선택할 수 있습니다.
- **파일 하나 = 시퀀스 하나**입니다. 기존 시퀀스에 추가하며 자동 실행하지 않습니다.
- 선택한 파일 중 하나라도 형식 오류나 이름 중복이 있으면 **전체 취소**합니다.
  기존 시퀀스와 선택 파일 사이에서도 이름은 대소문자를 무시하고 비교합니다.
  복사본을 추가하려면 JSON의 `Name`을 다른 이름으로 변경하세요.
- **시퀀스 관리 → 선택한 시퀀스 내보내기**를 누르면 작성 설명서 `_manual`을 포함한
  JSON 파일 하나를 저장합니다. 다른 PC의 Load에서 그대로 사용할 수 있습니다.
- `_manual`은 설명 문자열 배열입니다. 표준 JSON을 유지하면서 설명서를 파일 안에
  담습니다. AI에는 내보낸 파일과 장비 명령 규격을 함께 주면 됩니다.
- 실제 `//`, `/* */` 주석과 마지막 쉼표는 허용하지 않습니다. 명령별 설명은 `Comment`에 씁니다.
- 이전 `CommandSequences` 배열 예제나 전체 `default.json`은 이 전용 형식이 아닙니다.
  기존 프로필을 불러온 앱에서 시퀀스별로 Export하세요.
- 제한: 파일당 UTF-8 2 MiB, 한 번에 100개 파일, 시퀀스당 10,000개 명령.
  한 번의 Load에서 선택한 파일은 **합계 10,000개 명령 및 16 MiB** 이하여야 합니다.
  합계 제한을 넘겨도 일부만 추가하지 않고 전체 불러오기를 취소합니다.

## 2. 엄격한 JSON 규격 (버전 1 / RX Check용 버전 3)

필드 이름과 열거값은 대소문자를 구분합니다. 미지원 필드, 중복 키, 누락된 필수 필드,
잘못된 타입과 범위는 보정하거나 무시하지 않고 실패합니다. 숫자 문자열과 소수도 거부합니다.

| 위치 | 필드 | 규칙 |
| --- | --- | --- |
| 최상위 | `_manual` | 선택. 설명 문자열 배열. 실행에 영향 없음 |
| 최상위 | `FormatVersion` | 필수. TX만 있으면 `1`, RX Check가 있으면 `3`. 버전 `2`는 읽을 때 TX → RX Check로 확장 |
| 최상위 | `Name` | 필수. 공백이 아닌 문자열, 이름 중복 불가 |
| 최상위 | `RepeatCount` | 필수. 정수 1~9,999 |
| 최상위 | `Steps` | 필수. 명령 객체 배열. 빈 배열은 편집용으로 허용하지만 실행 불가 |
| 명령 | `Name` | 선택. 진행 표시·오류·CLI/MCP 단계별 결과에 쓰는 짧은 이름. 문자열 또는 null, 중복 허용 |
| 명령 | `IsEnabled` | 선택. boolean, 기본 `true`. `false`이면 해당 명령과 지연을 GUI·CLI/MCP 실행에서 제외하고 정의는 보존 |
| 단계 | `Kind` | 버전 3의 `"Tx"` / `"RxCheck"`. 기존 파일은 TX |
| 단계 | `CommandText` | TX 전송 내용. RX Check는 반드시 빈 문자열로 저장하여 이전 앱이 패턴을 송신하지 않게 함 |
| 단계 | `RxPattern` | RX Check의 기대 패턴. 1~4,096자. TX에는 사용 불가 |
| 명령 | `LineEndingMode` | 필수. `"None"`, `"Cr"`, `"Lf"`, `"Crlf"` 또는 null |
| 명령 | `DelayAfterMs` | 필수. 정수 0~600,000. TX는 전송 후 대기, RX Check는 전체 검사 시간 |
| 명령 | `Comment` | 선택. 단계 툴팁과 JSON에 남기는 설명 메모. 문자열 또는 null. 실행에 영향 없음 |
| 명령 | `TxMode` | 선택. null 또는 `"Terminal"`, `"Hex"`. null/누락 TX는 실행 시작의 메인 모드. RX Check는 같은 회차의 직전 활성 TX 모드를 따르며, TX가 없으면 메인 모드 |
| 명령 | `CaptureMs` | 선택. 정수 0~60,000, 기본 2,000. **CLI/MCP 실행**에서 전송 후 RX 수집 시간 |
| 명령 | `Expect` | 선택. null 또는 `{"Kind":"text","Value":"OK"}`. **CLI/MCP 실행**에서 수신 구간의 리터럴 확인 |
| 명령 | `ResponseCheck` | 이전 버전 2 읽기 전용. 별도 RX Check 단계로 변환하며 새 저장은 버전 3 사용 |

Step의 `Name`은 예를 들어 `펌웨어 버전 조회`처럼 실행 중인 단계를 알아볼 짧은 이름입니다.
GUI 진행 표시와 오류 메시지에 쓰이며 CLI/MCP 실행 결과의 단계 `name`에도 포함됩니다.
생략하거나 비워 두면 GUI는 `CommandText`를 대신 표시합니다. 단계 이름으로 실행 순서를
정하거나 다른 단계를 참조하지 않으며 중복되어도 됩니다. 중복할 수 없는 필수 이름은
**최상위 시퀀스 `Name`**입니다.

`Comment`는 예를 들어 `재부팅이 끝난 뒤 다음 명령 전송` 같은 참고 설명입니다.
목록의 단계 툴팁에서 이름과 메모를 함께 확인할 수 있습니다. 두 필드 모두 JSON/프로필에
저장되지만 장비에 전송되거나 실행 동작을 바꾸지 않습니다. CLI/MCP 정의에는 설명 메모
필드가 없으므로 GUI의 `Comment`를 자동화 입력에 추가하지 마세요.

`LineEndingMode: null`은 실행 시작 시의 메인 TX 줄 끝 설정을 사용합니다.
`"Global"`은 유효하지 않습니다. 큰따옴표와 역슬래시는 JSON 문법대로 이스케이프하세요.
화면 표시 속성(`DisplayName`, `StepNumber` 등)도 추가하면 실패합니다.

`Expect.Kind`는 정확히 `"text"` 또는 `"hex"`입니다. `Value`는 1~4,096자의 리터럴이며
공백·줄바꿈도 의미가 있습니다. HEX 값은 `"AA 01 FF"`처럼 완성된 바이트를 쓰고 공백을
사이에 넣을 수 있습니다. 정규식·순서만 맞는 부분수열 매칭은 지원하지 않습니다.
`OK`는 형식 예시일 뿐이므로 실제 제품 규격에서 의미가 확인된 응답만 지정하세요.

바로 불러올 수 있는 예제: [기존 TX 전용 버전 1](sequence_examples.json),
[문자·HEX RX Check가 있는 버전 3](sequence_rx_example.json).
명령은 형식 예시이므로 실제 장비에서 지원하는 것으로 바꾸세요.

## 3. 실행 동작과 제한

- 체크된 활성 Step만 순서대로 실행합니다. TX는 전송 후, RX Check는 검사하면서 각 `DelayAfterMs`만큼 기다립니다.
  비활성 Step은 전송과 지연 모두 건너뜁니다. 모든 Step이 비활성이면 실행할 수 없습니다.
  기존 파일에 `IsEnabled`가 없으면 모든 Step이 활성 상태로 열립니다.
  마지막 Step의 대기도 매 반복과 최종 종료 전에 적용됩니다.
- GUI Run에서 예제는 `status → 500ms 대기 → version → 1,000ms 대기`를 3회 반복합니다.
  설정된 대기 합은 4.5초이고, 실제 전체 실행에는 전송·스케줄링 시간이 더해집니다.
  정확한 주기나 실시간 타이밍을 보장하지 않습니다.
- 순수 대기 Step은 없습니다. 빈 명령을 넣지 말고 앞 명령의 `DelayAfterMs`를
  조정하세요. 첫 명령 전 대기는 별도 Step으로 표현할 수 없습니다.
- **GUI Run**에서 Auto reconnect가 활성화된 상태로 예기치 않게 연결이 끊어지면 시퀀스는
  진행 위치와 반복 횟수를 유지한 채 재연결을 기다립니다. 연결 복구 후 이어서 실행합니다.
  송신 성공한 Step은 재전송하지 않고, 연결 끊김으로 송신 실패한 Step은 재시도합니다.
  실패 직전에 장치가 명령을 받았을 가능성이 있으므로 해당 명령은 중복 수신될 수 있습니다.
  일시 대기·재개·재시도 메시지는 시스템 로그에 기록됩니다.
- 전송 후 대기 시간은 연결이 끊긴 동안에도 경과합니다. 다음 Step은 기존 대기 시간이
  끝나고 재연결도 완료된 뒤 실행합니다. 실행 시작 시 Mode와 Global 줄 끝 설정을 고정합니다.
- Stop, 수동 연결 해제, 앱 종료는 재연결 대기 중인 시퀀스도 취소합니다.
  자동 재연결이 비활성화되어 있거나 복구할 수 없는 전송 오류이면 중단합니다.
  Stop은 송신 대기에도 취소를 전달하지만 이미 전송된 바이트를 회수하지는 못합니다.
- **GUI Run**은 `TxMode`와 `DelayAfterMs`를 적용하며 `CaptureMs`·`Expect`는 실행하지 않습니다.
  TX만 있는 시퀀스는 장비 응답을 기다리거나 판정하지 않습니다. 응답 검사는 RX Check 단계에 지정합니다.
  조건 분기, 응답에 따른 재시도, 변수, 계산, 시퀀스 호출, 무한 반복은 지원하지 않습니다.

### GUI TX / RX Check와 실행 결과

**+ Step → TX / RX Check**로 단계를 추가합니다. 메인 목록은 `사용 | # | 유형 | 내용 | 모드 | 줄 끝 | ms`를 한 줄로 표시하며 이름·메모는 편집창의 선택 정보에 보관합니다.

예를 들어 메인 TX가 HEX 모드일 때 다음처럼 설정합니다.

| 사용 | # | 유형 | 내용 | ms |
| --- | --- | --- | --- | --- |
| ✓ | 1 | TX | `AA 10 01` | 20 |
| ✓ | 2 | RX Check | `AA 55 ?? 00` | 1000 |
| ✓ | 3 | TX | `AA 20 01` | 100 |

1. #1은 바이트를 전송하고 20ms 기다립니다.
2. #2는 기대 패턴을 검사하며 **1000ms 전체를 기다립니다**. 일찍 일치해도 시간을 줄이지 않으며 별도의 추가 대기는 없습니다. 이 시간은 항상 수정할 수 있습니다.
3. 일치·미확인 모두 #3으로 진행합니다. 분기나 응답에 따른 재전송은 없습니다.

응답 형식을 별도로 선택하지 않습니다. RX Check는 같은 회차의 직전 활성 TX 모드(없으면 실행 시작의 메인 모드)를 따릅니다. 기존 파일의 명시적 `TxMode`는 보존합니다. Terminal에서는 `READY` 같은 문자를 연결의 RX 인코딩으로, HEX에서는 `AA BB ?? 00` 같은 바이트 패턴으로 입력합니다. Terminal은 대소문자·공백을 구분하는 리터럴이며 HEX `??`는 한 바이트를 무시합니다. 부분 nibble(`A?`), `*`, 전체 와일드카드는 거부합니다. 활성 패턴은 첫 TX 전에 검증합니다.

RX Check는 직전 TX 직후부터 같은 연결에서 이미 받은 RX도 검사하여, 전송 후 대기 중에 도착한 빠른 응답을 놓치지 않습니다. 직전 TX가 없는 RX 전용 단계는 그 단계 시작부터 검사합니다. 회차가 바뀌면 이전 회차의 TX와 RX를 재사용하지 않습니다. TX 이후 연결이 바뀌어도 연결 변경 전에 패턴이 완성됐다면 일치로 처리합니다. 변경 전 RX만 검사하며, 재연결 이후 RX로 부분 패턴을 이어 맞추지 않습니다. 패턴은 RX 조각과 HEX 화면 묶음 경계와 관계없이 연속 바이트로 검사합니다. 문자 검사는 시작과 끝이 검사 범위에 모두 포함된 문자만 인정하며, 범위 앞의 바이트는 디코딩 상태 복원에만 사용합니다. 따라서 CP949 문자의 후행 바이트를 영문자로 오인하지 않습니다. HEX 검사는 범위의 원본 바이트를 그대로 검사합니다. 여러 RX Check를 연속 배치하여 같은 TX 이후의 서로 다른 패턴을 확인할 수도 있습니다.

일시정지는 현재 단계의 시간 전체가 끝난 다음 적용하고, Stop은 즉시 대기를 취소합니다. 연결 변경 전까지 일치하지 못했거나 검사 대상 연결에서 시리얼 오류·수집 유실이 발생하면 판정 불가로 구분합니다. 기존 `Expect`/`CaptureMs`는 CLI/MCP 전용으로 보존하며 RX Check로 변환하지 않습니다. 이전 버전 2의 TX 부속 `ResponseCheck`만 TX와 RX Check 두 단계로 읽고, 새 RX Check의 전체 대기 규칙을 적용합니다.

**실행 결과** 창에는 회차·단계·유형·시작 시각·결과와 다음 로그 기록을 표시합니다.

```text
21:13:58.319  TX  AA 10 01
21:13:58.340  RX  FE AA
21:13:58.345  RX  55 37 00 FF
```

TX 시각은 호스트 송신 시작, RX 시각은 원본 수신 조각을 받은 시각입니다. 작업 큐나 화면에 표시한 시각을 수신 시각으로 쓰지 않으며 장비 내부 시각이나 개별 바이트의 물리적 도착 시각은 아닙니다. 일치 부분을 강조하고 최초 일치 시각·연관 TX·응답 시간도 보여줍니다. 로그 기록은 실행 당시 단계의 Terminal/HEX 모드로 자동 표시하며, 회차·결과 필터와 이전 이력 조회를 지원합니다. 과거 시각 정보가 없는 이력은 `시간 기록 없음`으로 표시합니다. 결과 창을 닫아도 실행은 계속됩니다.

결과 창을 열어 둔 동안에도 새 실행 목록을 자동으로 갱신하며, 창을 다시 활성화할 때도 목록을 확인합니다. 갱신 중에는 선택한 실행과 RX 상세 내용을 유지합니다. 조회 중인 실행이 최신 100개 밖으로 밀리거나 일시적으로 목록에서 읽히지 않아도 선택한 한 개는 추가로 유지하며, 다른 실행을 선택하면 이전 항목의 보관 잠금을 해제합니다. 저장된 실행이 없으면 RX Check가 포함된 시퀀스를 실행하라는 안내를 표시합니다.

활성 RX Check가 있는 GUI 시퀀스만 별도 결과를 수집합니다. TX만 있거나 RX Check가 모두 비활성이면 기존 TX 경로를 유지합니다. 일반 Log ON/OFF와 독립적으로 `%LOCALAPPDATA%/SerialMonitor/sequence-runs`에 정의·요약·단계 JSONL/인덱스·64MiB 단위 원본 RX·수신 시각 인덱스를 비동기 저장합니다. UI는 결과 200행, RX 최대 16KiB/200조각씩 조회합니다. 긴 TX 미리보기는 제한하고 전체 TX는 `definition.json`에 보관합니다.

새 결과 파일은 축약된 v2 저장 형식을 사용합니다. 명령·검사 패턴은 `definition.json`에 한 번 저장하고 단계 JSONL에는 실행 중 달라지는 값만 기록합니다. 화면 표시 문자열은 조회할 때 만듭니다. RX 시각 인덱스는 수신 조각당 24바이트로 원래 조각 경계·수신 시각·연결 세대를 보존합니다. 원본 RX, TX/RX 시각 정밀도, 재시도·오류·일치 범위와 모든 조회 기능은 유지하며, 기존 형식의 이력도 그대로 읽습니다. 기존 파일을 자동으로 재작성하지는 않습니다.

실행당 RX 1GiB / 메타데이터 256MiB를 넘거나 저장이 실패하면 오류를 표시하고 다음 TX를 중단합니다. 보관 목표는 최근 100개 / 합계 4GiB이며 실행·조회 중인 이력은 보호합니다. 비정상 종료한 실행은 `interrupted`로 표시합니다.

**CLI/MCP 호환:** 기존 실행·수집·`Expect` 의미와 API는 유지합니다. 현재 자동화 API로 표현할 수 없는 활성 RX Check 또는 이전 ResponseCheck의 조회·실행과 해당 정의 덮어쓰기는 `unsupported_sequence_feature`로 거부합니다. RX 패턴을 명령으로 전송하거나 조건을 지우지 않습니다. 새 단계는 GUI / 버전 3 JSON으로 관리하고 CLI/MCP 결과는 기존 capture API로 확인합니다. RX 룰에서 시퀀스를 시작하는 기능과는 별개이며 실행 중 새 트리거는 무시됩니다.

### GUI 편집과 단계 실행

- 각 행의 사용 체크박스로 Step을 임시 비활성화할 수 있습니다. 체크 상태는
  프로필과 내보낸 JSON에 보존되며, 다시 체크하면 원래 순서로 실행됩니다.
  진행률은 활성 Step 수를 기준으로 계산하고 현재 단계에는 원래 행 번호를 표시합니다.
- **단계 복제**는 선택한 Step 바로 아래에 독립된 복사본을 만듭니다.
  **시퀀스 복제**는 관리 메뉴에서 사용할 수 있으며 중복되지 않는 이름을 붙입니다.
- 실행 조작은 **▶ / Ⅱ 버튼 하나**로 합니다. 대기 중 `▶`를 누르면 시작하고,
  실행 중 `Ⅱ`를 누르면 현재 Step의 전송과 지연이 끝난 뒤 다음 Step 직전에 일시정지합니다.
  버튼은 `▶`로 바뀌며 다시 누르면 이어서 실행합니다. 일시정지 요청 중에도 `▶`를 누르면
  요청을 취소하고 계속합니다. 상태에는 요청 중 `Pausing`, 실제 대기 중 `Paused`를 표시합니다.
  **Stop**은 실행을 끝내므로 다음 시작은 처음부터 진행합니다.
- 단계 목록에는 명령만 한 줄로 표시합니다. 선택적 이름과 메모는 편집창·툴팁에 보존합니다.
- 사용자 일시정지는 자동 재연결 후에도 유지됩니다. **Stop**은 일시정지·재연결
  대기도 취소합니다. 이 조작들은 일반 GUI 실행에 적용되며 CLI/MCP 실행에는
  기존 시작·상태·취소 제어를 사용합니다.
- 실행 중에는 체크 상태와 명령 편집을 잠급니다. GUI 실행은 기존처럼 전송과
  지연만 수행하며 장비 응답 성공/실패 판정이나 조건 분기를 추가하지 않습니다.

### Terminal과 HEX

| 항목 | Terminal | HEX |
| --- | --- | --- |
| `CommandText` | 장비에 보낼 텍스트 | `AA 55 01 00`처럼 2자리 바이트를 공백으로 구분 |
| 전송 내용 | 현재 구현은 UTF-8 텍스트 + 지정한 줄 끝 | 입력한 바이트 그대로 |
| `LineEndingMode` | 적용됨 | 무시됨. 명확하게 `"None"`으로 작성 권장 |

`TxMode`가 null이거나 없으면 **실행 시작의 메인 Mode**를 사용합니다.
`"TxMode":"Terminal"` 또는 `"TxMode":"Hex"`를 지정하면 해당 Step은 명시한 형식으로
전송하므로 한 시퀀스에 두 형식을 함께 넣을 수 있습니다. 실행 전에 모든 HEX Step을
검증하며 하나라도 잘못되면 첫 명령부터 전송하지 않습니다. 비활성 Step은 실행 검증에서
제외됩니다. GUI Step 편집창에서 Global/Terminal/Hex를 선택할 수 있으며, `CaptureMs`와
`Expect`는 보존하고 툴팁에 표시합니다. 응답 설정은 JSON 또는 CLI/MCP로 변경하세요.

HEX의 `AA 55`는 문자 A와 A가 아니라 0xAA, 0x55 두 바이트입니다.
줄 끝이 필요하면 `0D 0A`처럼 직접 포함해야 합니다. 길이·체크섬·CRC를 앱이
계산해 주지 않으므로 장비 규격에 맞는 완성된 바이트를 작성해야 합니다.
체크섬 규격이나 명령 의미가 없으면 AI가 추측해 만들지 않게 하세요.
명시적 `TxMode`가 있으면 명령 앞뒤 공백·줄바꿈을 그대로 보존합니다. 누락/null인
기존 Global Step은 기존처럼 앞뒤 공백을 제거합니다. Terminal 명령에 줄 끝이 이미
포함되어 있다면 `"LineEndingMode":"None"`을 사용해 중복 추가를 피하세요.

### CLI/MCP 실행의 RX와 응답 확인

등록된 시퀀스를 CLI/MCP로 실행하면 명령 전부터 원본 RX를 구독하고, 각 Step 전송 후
`CaptureMs`만큼 수집한 다음 `DelayAfterMs`를 기다립니다. 전체 RX는 저장 파일과
페이지로 확인할 수 있습니다. 선택한 리터럴의 일치 여부는 참고 정보이며, 섞인 printf로
일치하지 않아도 제품 실패를 뜻하지 않습니다. 일치 여부와 별개로 실제 RX를 읽어 판단하세요.

RX는 수신 chunk나 HEX 화면의 byte timeout 묶음과 별개인 원본 바이트 순서로 수집합니다.
응답이 여러 chunk로 분리되거나 여러 패킷이 한 chunk로 합쳐져도, 수집 구간 안의 정확한
연속 바이트를 확인합니다. 한 줄이나 한 chunk를 패킷 경계로 보지 말고 필요하면 제품의
헤더·길이·체크섬/CRC로 검증하세요. 응답이 수집 구간보다 늦으면 `CaptureMs`를 늘립니다.

CLI의 `configure --port COM7 --baud 57600 --byte-timeout-ms 80` 또는 MCP의
`serial_configure` (`port`, `baudRate`, `byteTimeoutMs`)로 현재 연결의 호스트 BPS와
HEX 화면의 byte timeout을 바꿀 수 있습니다. BPS는 1..10,000,000 범위에서 드라이버가
지원해야 하며, byte timeout은 1..5,000ms(기본 40ms)입니다. 제품의 BPS 변경 명령은
별도로 제품 규격에 따라 보내야 합니다. 이 설정들은 Step 필드가 아니므로 시퀀스 JSON에
임의로 추가하지 말고 실행 전후 별도 제어 요청으로 적용합니다.

Windows·USB·RS485 전환과 처리의 지연 변동을 고려해 이론적인 바이트 간격보다 여유 있게
timeout을 잡고 실제 수신으로 조절하세요. byte timeout은 화면 묶음 기준이며 패킷 경계를
보장하지 않고, 전체 응답을 기다리는 `CaptureMs`를 대신하지 않습니다. 실행 중 설정
변경은 `busy`이므로 시퀀스가 끝난 뒤 적용합니다.

자동화 실행은 연결이 바뀌거나 TX 결과가 불확실하면 중단하고 자동 재전송하지 않습니다.
취소해도 이미 보낸 바이트는 되돌릴 수 없습니다. 실행 시작 후 받은 실행 ID로 진행률과
결과를 조회하고 취소할 수 있습니다. GUI Stop 또는 AI/CLI 취소도 사용할 수 있습니다.

GUI 파일의 최대 크기·반복 수와 별도로 자동화 실행에는 더 작은 한도가 적용됩니다.
반복을 포함한 실행 Step 수 128개, 수집+대기 합계 10분, Step별 수집·대기 각각 60초·600초,
명령 16,384자, 이름 128자, 정의 UTF-8 JSON 48 KiB를 넘으면 실행하지 않습니다.
API의 소문자 필드 형식은 이 GUI 파일의 PascalCase 형식과 구분합니다.
`sequence get`은 활성 Step만 담은 실행 정의를 반환합니다. 비활성 Step까지 보관·공유하려면
GUI JSON 내보내기를 사용하세요. CLI/MCP `sequence save`의 명시적 덮어쓰기는 기존과
동일하게 전체 정의를 교체하므로, 실행 정의만 다시 저장하면 비활성 Step은 포함되지 않습니다.
자세한 명령·등록 형식은 [AI 제어 안내](ai_control.md)를 참고하세요.

## 4. AI에게 줄 요청문

내보낸 JSON 파일을 첨부하고 다음 요청을 사용하세요.

```text
첨부 JSON의 _manual을 지켜 GUI 불러오기용 시퀀스를 작성해 주세요.
TX만 있으면 FormatVersion:1, RX Check가 있으면 FormatVersion:3을 사용하세요.
빈 양식이 버전 1이어도 RX Check를 요청하면 버전 3으로 바꿔 주세요.
파일 하나에 시퀀스 하나만 넣고 _manual 설명도 유지해 주세요.

- 시퀀스 이름:
- 장비/펌웨어와 실제 지원 명령 또는 완성된 HEX 패킷:
- 메인 모드와 필요한 Step별 TxMode (null/Terminal/Hex):
- 줄 끝 (None/Cr/Lf/Crlf 또는 null):
- 각 단계 유형(TX / RX Check), 전송 내용 / 기대 패턴, 대기·확인 시간(ms):
- 전체 반복 횟수:
- CLI/MCP 실행 시 필요한 RX 수집 시간(CaptureMs)과 문서에 있는 리터럴 응답(Expect):
- 기존 시퀀스 이름 (중복 방지):

이미 제공한 정보는 다시 묻지 말고 모르는 명령·응답 패턴·체크섬은 먼저 확인해 주세요.
버전 3의 각 단계에는 Kind:Tx 또는 RxCheck를 지정하세요. RX Check는 CommandText를
빈 문자열로 두고 RxPattern에 기대 패턴, DelayAfterMs에 전체 검사 시간(0..600000)을
씁니다. TX의 DelayAfterMs는 전송 후 대기입니다. RX Check는 일찍 일치해도 검사 시간을
모두 기다리고 같은 회차 직전 TX 이후 받은 응답도 확인합니다. RX TxMode:null은 직전
활성 TX 모드, 없으면 메인 모드를 따릅니다. 문자 패턴은 대소문자·공백이 유효한 리터럴,
HEX의 ??는 한 바이트 와일드카드이며 적어도 한 고정 바이트가 필요합니다.
새 파일에 이전 ResponseCheck나 TimeoutMs를 넣지 마세요.
CLI/MCP 실행용은 TX만 있는 버전 1과 기존 CaptureMs/Expect를 사용하세요. 두 필드는
GUI RX Check를 켜지 않습니다. 현재 CLI/MCP는 RX Check와 HEX 기대값의 ??를 지원하지
않으므로 이를 등록·실행했다고 안내하지 마세요. 이 GUI PascalCase JSON을 소문자
CLI/MCP 등록 API에 직접 넣지 마세요. 직접 등록이 목적이면 별도 자동화 규격을 확인하세요.
섞인 printf 때문에 불일치만으로 제품 실패를 판정하지 마세요. 분기 등 지원하지 않는
요구는 임의 필드로 만들지 마세요.
코드 블록이나 JSON 주석 없이, UTF-8로 저장 가능한 표준 JSON 하나를 출력해 주세요.
```
